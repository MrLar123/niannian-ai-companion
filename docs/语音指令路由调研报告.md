# 调研报告：语音指令路由——让小芸"听懂"切音色、做动作

> 日期：2026-10-19 ｜ 范围：业界方案调研 + 对小芸现有架构的落点分析
> 结论先行：**业界共识是"分层路由"——确定性规则层前置、LLM 兜底**。小芸不需要引入新框架，在 `/api/chat` 与 `/api/chat_stream` 入口加一层轻量指令路由器，复用已有的 `/api/voice-options` 与 `/api/motion` 即可落地。

---

## 一、业界方案四个流派

### 1. 传统智能语音助手管线（小爱同学 / 天猫精灵 / Alexa / 讯飞）
经典四级流水线：

```
ASR 文本 → NLU（领域识别 → 意图识别 → 槽位填充）→ 对话管理（DM）→ 技能路由 → 执行/回复
```

- 核心思想：**指令与闲聊是两种不同的路由目标**。NLU 先判"这是指令还是闲聊"，指令走技能表（结构化执行），闲聊走对话引擎。
- 实体抽取解决参数问题："把声音换成御姐" → 意图=`切音色`，槽位=`音色名=御姐`。
- 意图置信度阈值（业界通常 >0.9 才直接执行）过滤误触发，不足时反问澄清。
- 启示：**路由判定必须发生在对话大脑之前**，不能指望闲聊 LLM 顺便执行指令。

### 2. LLM 时代的统一方案（Function Calling / Tool Use）
OpenAI、Anthropic、Qwen 等主流模型均支持 tool use：把"切音色""播放动作"注册为带 schema 的工具，LLM 在对话中自主决定调用。

- 优点：自然语言泛化最好，"你唱一首歌吧"也能映射到 `play_motion(dance)`。
- 缺点：**增加一轮 LLM 延迟**（小芸走 or_proxy 免费池，实测 1~3s 起）；OpenRouter 免费池中并非所有模型都稳定支持 tool calling；指令执行速度反而比规则慢。
- 业界现状：纯 LLM 路由多用于云端助手；**延迟敏感的桌宠场景不选纯 LLM 方案**。

### 3. Vtuber 生态（VTube Studio API / AI 主播实践）
与桌宠最接近的参照系，做法非常一致：

- **关键词 → 热键映射**：弹幕/语音出现"谢谢、666、跳舞"等关键词，正则命中即通过 API 触发对应动作/表情（`HotkeyTriggerRequest`）。VTS 官方事件系统 + 社区插件全是这个模式。
- **LLM 回复内嵌情绪标签**：让对话 LLM 在回复前输出 `[Happy]/[Angry]` 等标签，程序解析标签触发表情——即"LLM 出标签、程序出动作"，不让 LLM 直接控制执行。
- **冷却机制**：同一动作设冷却时间，防止连发造成视觉疲劳。
- **一次性动作 vs 持久态**：VTS 区分 Play motion（播一次）与切换 idle motion（持久）。这是动作系统的两种语义。

### 4. 混合分层路由（当前业界主流共识）
将 1+2 组合，按"延迟要求 × 说法泛化需求"分层：

| 层 | 手段 | 延迟 | 覆盖 |
|---|---|---|---|
| L1 确定性规则 | 关键词/正则 + 槽位模糊匹配 | <1ms，离线 | 高频固定说法（占指令绝大多数） |
| L2 LLM 兜底 | function calling | 1~3s | 自然说法、组合指令 |
| L3 对话 | 现有闲聊链路 | 不变 | 未命中任何指令意图 |

规则层优先命中、LLM 兜底、都不中才走对话——这是小爱/天猫精灵/车载助手演进后的通用形态。

## 二、小芸现状盘点（调研时实测确认）

| 能力 | 现状 | 结论 |
|---|---|---|
| 语音入口 | ASR 文本 → `/api/chat` / `/api/chat_stream` → `_brain_turn()` → or_proxy | **全部进对话大脑，无指令分流** ← 缺口所在 |
| 音色库 | `VOICE_OPTIONS + GSV_OPTIONS + VOLC_OPTIONS` 三组注册表；`POST /api/voice-options` 热切换+持久化；托盘已在用 | 执行端**现成**，只缺"语音触发" |
| 动作库 | `assets/motions/*.vmd`（14 个动作+同名 json 显示名）；`GET /api/motions` 列表、`POST /api/motion` 切换（写 current.txt，页面 2s 内自动切） | 执行端**现成**；但语义是**持久切换**，无"播一次回 idle" |
| 本地 GSV 拉起 | 切到 gsv: 音色时后台拉起 GPT-SoVITS（30~60s），不阻塞 | 语音切音色需要提示"声音准备中" |
| 发声确认 | `_publish_reply()` 共用函数（SEQ/GUARD/PLAYBACK 时序铁律） | 指令确认话术**必须**走它，禁止另写发布逻辑 |

本机 AI-Vtuber 整合包（小芸前身）的"指令"主要是键盘映射与本地问答库，无成熟意图路由可借，参考价值低于 VTS 生态。

## 三、推荐方案：两层指令路由器（新增 `voice_command_router.py`）

```
ASR 文本
   │
   ├─ L1 规则层（<1ms，纯离线）
   │    意图识别：触发词表（换声音/换个音色/来首…跳个舞/做一个动作/停下…）
   │    槽位填充：音色名/动作名 ↔ 注册表 label+key+别名，difflib 模糊匹配
   │    ├─ 命中且置信够 → 直接调 _apply_voice() / 写 MOTION_STATE
   │    │                 → 确认话术走 _publish_reply()（复用时序铁律）
   │    └─ 命中但槽位模糊（如音色名含糊）→ 她反问确认，不瞎切
   │
   ├─ L2 LLM 兜底（Phase 2 可选）：给 or_proxy 请求挂 tools schema，
   │    支持"你唱首歌吧"这类无关键词说法；免费池不支持 tool 的模型自动跳过
   │
   └─ L3 现状对话链路（未命中，行为零变化）
```

**设计要点：**
1. 路由器挂在 `/api/chat` 与 `/api/chat_stream` 共同入口（两路都拦），对现有代码零侵入——命中才改道，未命中逐字节保持原行为。
2. 音色槽位对三组注册表的 label/id/别名做匹配（如"御姐"→ volc/minimax 御姐系，"本地xx"→ gsv:xx）；动作槽位对 `_list_motions()` 的 key/label 匹配（json 里的显示名天然就是语音别名）。
3. 一次性动作：Phase 1 用现有持久切换（最小实现）；Phase 2 给页面加 one-shot 播完回 idle 的语义（VTS 的 Play motion 模式），"跳个舞"才真正自然。
4. 冷却防抖：同一动作 10s 冷却（借鉴 VTS 弹幕互动实践）。
5. 确认话术 + gsv 拉起提示都走 `_publish_reply()`，不复制发布逻辑（时序铁律红线）。

## 四、实施阶段建议

- **Phase 1（约一个文件 + 两处入口各 3 行）**：L1 规则路由，音色切换 + 动作持久切换 + 确认话术 + 冷却。
- **Phase 2**：动作 one-shot 语义（页面侧）；L2 function calling 兜底（按 or_proxy 模型池实测支持度决定是否上）。
- **Phase 3（可选）**：指令接入长期记忆（"她记得你喜欢御姐音"）。

## 五、风险与已知坑

| 风险 | 对策 |
|---|---|
| ASR 误识别音色名（"玉双"↔"御姐"） | difflib 模糊匹配 + 相似度阈值，低于阈值时她反问确认而非乱切 |
| gsv 音色首次切换 30~60s 拉起 | 话术明示"正在准备这个声音"，后台 gsv_wait_ready 已有 |
| 指令被工作态门控/主动搭话逻辑干扰 | 指令是用户显式发言，在 chat 入口拦截，不经过 CTX 门控分支 |
| 确认语音触发自听死循环 | 全部走 `_publish_reply()`，守卫机制自动生效 |
| 切动作与 VMD 播放中状态冲突 | 页面现有 2s 轮询自动切换已处理，Phase 2 one-shot 需另行验证 |

### 一、匹配层修掉的两个真缺陷（`voice_command_router.py`）

| 缺陷 | 现象 | 根因 | 修法 |
|---|---|---|---|
| 时长注记读成名字的一部分 | 改名后动作名变成「弹跳扣扣舞 · 8 秒」 | `clean_label()` 只剥括号里的注记，剥不掉 `· 8 秒` | 追加规则：末段以数字开头就当作时长剥掉；服装名（泳装/旗袍）保留 |
| 前缀互相吞并 | "换成卡芙卡泳装" 换成了基础版卡芙卡 | 短名 `卡芙卡` 命中即停，没有"整名优先"的概念 | 候选分两类：**整名命中给 FULL_BONUS**，拆段命中只按长度；再叠 `_norm()` 去掉间隔号/标点（"卡芙卡泳装" 才能对上「卡芙卡 · 泳装」） |

### 二、新增第四类指令：换性格（`switch_preset` / `ask_preset`）

- 锚点：`性格 / 人设 / 人格 / 脾气 / 性子 / 调调 / 口吻 / 态度`。
- 与音色的**冲突消解**（关键取舍）：`温柔` 既是音色别名也是性格名。规则是
  「有名词锚点 → 性格」；没有锚点时只认**与音色别名不重叠**的性格词（傲娇/毒舌/女王…）。
  于是"换个温柔的声音"仍然换音色，"换成温柔的性格"才换人格 —— 上一版的听感不变。
- 反问：没点名（"换个性格呗"）报前 5 套；同名词歧义报候选二选一。
- 冷却 8s；已是当前人格时不重复加载（`_apply_preset` 会重算语速/声线）。
- 状态隔离：`tools/test_voice_command_wiring.py` 现在把 `PRESET_STATE` 也指到临时目录 ——
  否则跑一次测试就把用户当前人格改掉了。

## 实施记录（Phase 2 + Phase 3 完成，2026-11-05）

> 本节取代上面「实施阶段建议」与各节里 Phase 2/3 的待办状态。三件事全部落地：
> 动作 one-shot、**ASR 误识别反问且不静默**、指令偏好记忆。

### 一、动作 one-shot：语音说"跳一遍" ≠ 菜单"从此循环这支"

| | 菜单/托盘点选 | 语音说「跳个舞」 |
|---|---|---|
| 语义 | 持久切换 | 播一次回待机 |
| 落点 | `assets/motions/current.txt` | 内存 `ONESHOT = {key, seq, at}`，**不写盘** |
| 页面 | `LoopRepeat` | `LoopOnce + clampWhenFinished`，播完停末帧再回 idle |

- **seq 递增而不是比 key**：同一支舞连说两次 key 不变，只有 seq 变了页面才认作新请求。
- **结束判定放在渲染循环 `tickOneshot()`**，判据 `danceAction.time >= clip.duration - 0.02`；
  放进原来的 2s 轮询会让停止时刻最多滞后 2 秒，舞跳完了还干站着，很难看。
- 播完 `POST /api/motion_done`（带 key 校验，旧请求返回 `stale=True` 不误清），
  服务端顺手 `pop` 掉该动作的冷却 —— 冷却本来只防 VAD 抖动连发，
  "跳完了再跳一次"是明确的第二次请求，不该被挡。
- 一次性动作没播完就喊停：`stop_motion` 同时 `_clear_oneshot()`，否则下一轮它又会起来。

### 二、ASR 误识别：从"乱切"和"静默"之间找第三条路

调研报告风险表只写了"模糊匹配 + 反问确认"，实测下来有两头都不能踩：

| 坑 | 现象 | 结论 |
|---|---|---|
| 近似用来**执行** | 「换成甘雨」被比成音色「晓雨」（两字名错一字相似度 0.5，而不相干的两字名只要共用一个字也是 0.5） | **两字名执行层禁用近似**（`_fuzz_threshold` 返回 1.01）；三字以上要 `FUZZ_MIN=0.72` 且甩开第二名 `FUZZ_GAP=0.06` |
| 禁用近似后**静默** | 「换成甘兩」三张表全没对上 → 返回 `None` 落闲聊，用户以为换装成功 | 加 `ask_clarify`：动词明确 + 非问句 + 全空时，**拿最像的名字反问** |

关键取舍：**近似只用来报候选，绝不用来改状态**。错了最多多问一句，不会切错。
反问候选走独立的 `loose_candidates()`（两字名门槛 0.5、不要求甩开第二名、最多 3 个），
与执行层的 `FUZZ_MIN` 完全隔离。三道闸门防打扰：

1. 必须有明确换/切动词（`_CHANGE_VERB`）且不是问句（`_QUESTION_RE`）；
2. 去掉动词/语气词后至少还剩 2 个字（"换成吧"由既有缺槽位反问处理）；
3. **一个像的候选都找不到就不反问** —— 「换成现金」、闲聊、问句全部安静交还对话。

反问不是死胡同：`CLARIFY_PENDING`（45s TTL）挂住候选，用户回「对 / 第一个 / 甘雨」
就合成一句带精确名字的话回放给 `_try_voice_command`，**复用原执行链**，不复制切换逻辑。
带了换/跳动词的新指令（「变成雷神」）会先让 pending 作废再正常解析，不会被确认态吞掉。

### 三、指令偏好记忆（Phase 3）

- `data/cmd_prefs.json`：按 `voice / motion / model / preset` 四类记 `key -> {count, last, label}`，
  只在指令**成功执行**时累加，原子写（`tmp + os.replace`），写失败只记日志、绝不影响指令。
- 用途只有一处：反问时 `_pref_hint()` 把常点的排前面，再补清单里没点过的。
  **不写死清单**（音色会增删，2026-11-05 刚加过 6 个女声），也**不参与任何执行判断** ——
  她记着你喜欢什么，但不替你决定。
- 与长期记忆（`memory.db`）刻意分开：指令偏好是行为计数，不是值得进语义检索的事实。
