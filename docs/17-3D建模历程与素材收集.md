# 17 — 3D 建模历程：从 VRoid 到 Avaturn

> 记录用过的 3D 软件、素材收集网站、最终 Avaturn 导出路线，以及
> "为什么语言模型编辑 3D 这么难"的第一手分析。全部为本机实操记录，非教程搬运。

## 1. 软件与工具链总览

| 软件/服务 | 用途 | 本项目中的实际角色 |
|---|---|---|
| **VRoid Studio**（免费） | 动漫风人形建模 | 服装/发型素材的导入目标；素材清单围绕它建 |
| **Blender 4.5.9**（便携版） | 减面/绑骨/贴图/格式转换 | 3D 管线主力：stageA 减面 → stageB 绑骨 → stageC 导 VRM |
| **Unity**（含 VRM 插件） | VRM 格式验证与动画 | 备用验证环境（最终用 three.js 页面替代） |
| **PMX Editor** | MMD 模型直接编辑 | 检查 PMX 模型结构、修骨骼权重参考 |
| **混元 3D（Hunyuan3D-2mini/2mv）** | AI 图生 3D（本机部署） | 白模与贴图生成 |
| **Avaturn**（网页服务） | 照片→3D 人脸 | 最终脸部来源 |
| **three.js + three-vrm**（网页） | 渲染验证 | 桌宠直接渲染环境，替代 Unity 做日常验证 |

**为什么最终选 Avaturn 而不是继续手建**：单图 AI 生成（混元）的全身脸必然是平的
（512² 输入里脸只占约 42px，与面数/参数无关）；手建需要数周级学习成本；
Avaturn 用一张正脸照片 20 分钟出带 187 个表情 morph 的可驱动头——质量/成本比碾压。

## 2. 素材收集网站清单

| 网站 | 内容 | 版权注意 |
|---|---|---|
| **BOOTH**（booth.pm） | VRoid 服装/发型/鞋袜 `.vroidcustomitem` 与贴图，免费+付费 | 免费也要登录 pixiv 走"无料下载"；少数带 SAMPLE 水印 |
| **模之屋**（aplaybox.com） | PMX 模型（姵儿/甘雨/雷电将军等 16 只） | 逐模型授权不同：可改造/可二次配布需署名/商用需联系 |
| **Bowlroll** | MMD 配布镜像（动作 .vmd 常在这） | 同模之屋体系授权 |
| **Nicovideo 3D 频道** | MMD 动作原发地 | 需日本账号，部分仅限日本 IP |
| **CGTrader** | 写实 FBX 素材（本项目买过 9 个，全部无骨骼） | 按商品授权；**注意很多静态模型无 armature** |
| **GitHub / hf-mirror** | three.js/three-vrm 库、模型权重 | 主域被墙走镜像：codeload/raw 可达 |

**BOOTH 搜索技巧**（实测有效）：URL 加 `?max_price=0&sort=pop` = 只看免费+人气排序
——`free=true` 参数无效是踩过的坑。完整免费素材清单见 `xiaoyun/docs/` 与 `vroid_ref/`。

## 3. 路线一：VRoid Studio（动漫风，素材拼装）

**流程**：VRoid 建素体 → BOOTH 下载服装/发型 `.vroidcustomitem` → 导入穿戴 → 导出 VRM。

**实测结论**：
- 优点：零建模基础可出标准二次元形象；素材生态最丰富；
- 局限：风格锁死在 VRoid 的默认体型/脸型框架内；直接导入 FBX **不被支持**
  （VRoid 只吃自家 `.vroidcustomitem`/`.xwear`/贴图 PNG）；表情 morph 有限；
- 本项目产出：JK 制服形象素材包（白衬衫+灰格裙+领结，与目标截图几乎一致），改色后备用。

## 4. 路线二：MMD（PMX）+ PMX Editor

**流程**：模之屋下载 PMX → （可选 PMX Editor 检查/修模）→ MMDLoader 直接进 three.js 页面。

**实测关键坑**：
- PMX 骨骼**全日文无英文名**（センター/上半身/首/頭…），必须先解析真实骨骼名再写驱动代码
  ——手写 PMX 解析器容易错，用现成 mmdparser；
- 驱动时センター（hips）必须锁死，一动整个人平移（"幽灵感"）；
- 贴图路径不带 tex/ 前缀 → 404 → 材质全丢，纹理要复制到 PMX 同级；
- 打光总强度 ≤2.0（赛璐璐材质极易爆白）；
- 舞蹈 .vmd 是日文骨名 + 左手系，VRM 重定向要全骨铺基准姿态再叠轨道。

**产出**：16 只 PMX 模型 + 15 套舞蹈，是当前桌宠的主力形象库。

## 5. 路线三：AI 生成（混元 3D 本机）+ Blender 后处理

**流程**：设定图/Seedream 出三视图 → 抠图 → 混元 gen_shape（单图或四视图）→
Blender stageA 减面 → stageB 绑骨 19 骨 → stageC 导 VRM → fix_vrm_restpose → stageT 三视图贴图。

**实测瓶颈（为什么这条路没走到脸）**：
1. **全身生成的脸必然平**：512² 输入、8.5 头身 → 脸宽约 42px、眼睛约 8px；
   mv 融合把正面细节平均掉；输入分辨率改大直接 shape mismatch（位置编码锁死 512）；
2. 头身分离方案（头部特写单独生成 + graft 拼接）：几何上成立但**两套头发拓扑对不上**，
   整头 graft 不可行；改"只取脸"（FACE_ONLY 沿深度切）才勉强可用；
3. 蒙皮：`ARMATURE_AUTO` 在 875k 顶点上**静默失败**（权重全空）——大网格必须手写距离权重；
4. 侧视贴图：重叠双壳没有遮挡判断，头发糊上肤色——**正/背投影是唯一稳定组合**。

**结论**：这条路能出身体和衣服，脸交给 Avaturn。

## 6. 路线四（最终采用）：Avaturn 照片重建

**流程**（免费档全流程，实测三次迭代）：
1. 用 Seedream 图生图做**真人自拍风格三视图**（正/左/右半身，浅灰墙、裸妆、黑长直全部耳后）
   ——Avaturn 要的是"像自拍的照片"不是设定图；
2. `hub.avaturn.me/create/upload` 上传（绕过 /create/scan 重定向 bug；主域需代理，本机 10809/13128 可达）；
3. 编辑器选发型/服装 → 导出选"头像（T字姿势）"= 全身 T-pose 绑定；
4. **免费档导出必须经 Discord 机器人 `#bot` 频道 `/avaturn` 点 Export GLB 解锁**；
5. GLB → Blender `glb2vrm.py`（Mixamo 骨名→VRM 标准骨 44 根重命名 + 表情 preset 绑定）→ avaturn_nn.vrm。

**三版迭代数据**：

| 版本 | 面数 | 骨骼 | morph | 关键差异 |
|---|---|---|---|---|
| avaturn1 | 32,071 | 52 Mixamo（含全手指） | 0 | 默认导出无 ARKit blendshape |
| avaturn2 | 28,715 | 52 | 0 | 脸明显更贴照片；编辑器加了眼镜+波波头（不符） |
| **avaturn3_final** | 22,668 | 54（含眼球骨 Eye_L/R） | **187**（ARKit52+16 viseme+jaw） | 导出时勾选了 morph；黑长直+白衣贴图调色（glb_swap_tex.py 原地重建 GLB binary） |

**morph 导出陷阱**：文档宣传有 ARKit，实际 v1/v2 免费导出没有，第三版导出时带上了
——**每次导出后必须用 glbview/vrm_check 数 morphMeshes**，不能信文档。

**成果**：照片级脸 + 187 morph（眨眼/口型/表情全可驱动）+ 拓扑规整 + 22k 面桌宠级体量。

## 7. 为什么语言模型（我）编辑 3D 这么难

这段是给"下一个想用 LLM 做 3D 管线的人"的第一手复盘。

### 7.1 不可见性：文本接口对不上空间数据

语言模型操作的天然对象是**文本**。3D 模型的本体是几十万顶点的浮点数组 +
拓扑连接表 + UV + 权重——全部既看不了（没有全局"长相"的概念）也说不完
（一个 VRM 的二进制 chunk 描述就要几万字）。于是每次编辑都退化成
"写脚本 → 跑 Blender/解析器 → 渲染截图 → 看结果"的**盲迭代循环**，
而截图验证本身又有坑（DPI 缩放 1.25 倍坐标偏移、clay 材质单面剔除会把脸整片剔掉
误判成"后脑勺"——同一模型两种材质渲染出两种朝向结论，我反复误判过三次）。

### 7.2 坐标系与约定的"隐形知识"

- Y-up 还是 Z-up？+Z 是脸还是背？（混元管线 **+Z=正面**，但"侧视图鼻尖朝画面右"才能定论；
  凭胸/臀凸出量判断朝向**不可靠**——背后长发厚度会污染统计）
- 左手系还是右手系？（MMD 左手系 vs three.js 右手系，VMD 四元数 x/y 取负）
- 朝向错误不会报错，只会"生成的模型脸完全平掉、没有五官"——而身体左右对称看不出来，
  最快的判断信号居然是"看正面白模有没有眼窝鼻梁"。
这类约定散落在各软件的导出器里，文档不写、报错不说，只能靠"渲染出来不对→反推"。

### 7.3 连锁修改：一个参数牵动整个管线

减面量影响蒙皮上限（875k 顶点静默失败）；绑骨层级影响 VRM 人型映射完整性
（肩骨必须是 UpperArm 父级，否则 humanoid 从 19 掉到 17 且**不报错**）；
贴图投影窗口要和 UV 块错开、UV 要 clip 到块矩形、高度场只收"亮+低饱和"面片——
每一条都是改一次错一次才沉淀的约束，且互相耦合。语言模型单轮上下文里
很难同时持有这十几个隐式约束，改 A 坏 B 是常态。

### 7.4 数值无直觉：差 0.1 和差 10 倍长得一样

文本里 "scale=0.616" 和 "scale=0.7" 没有视觉差异感，但 0.616 会让弹簧骨把刘海顶飞
（刚度/碰撞半径是世界单位，模型缩小 1/s 倍 = 相对刚度放大 1.62 倍）。
这类"数值错但渲染只是微妙不对"的问题，没有视觉基准的模型只能靠
A/B 渲染对比 + 物理推理，效率远低于人类建模师拖一下滑块。

### 7.5 什么情况 LLM 反而擅长（公平记录）

- **管线脚手架**：Blender Python 批处理、格式转换（GLB binary chunk 原地重建）、
  解析器（PMX/GLB/VMD）——纯代码、可断言、可回归，这正是本项目 3D 管线全部自动化的部分；
- **约束沉淀**：把踩过的坑写成 assert/检查脚本（nfix=0 法线修复、morphMeshes 计数、
  vrm_check 诊断页），让下一次迭代不重复交学费；
- **多方案枚举**：FBX 路线 vs PMX 路线 vs Avaturn 路线的取舍分析、授权条款比对。

### 7.6 结论

> LLM 做 3D 的瓶颈不在"会不会写 Blender 脚本"（会，且写得不错），
> 而在**闭环里缺一双眼睛**：空间结果不可见、渲染验证有陷阱、隐式约定靠踩坑获得。
> 实践上最优解是"LLM 写管线 + 确定性检查脚本 + 人看一眼定案"的分工——
> 本项目最终形态（混元白模 → Avaturn 照片脸 → Blender 脚本后处理 → three.js 渲染验证）
> 正是这个分工的产物。
