# AI 赛博女友 / AI 伴侣技术调研与「小芸」集成方案

> 调研时间：2026-11-04　|　对象项目：LunaAI / project-nn/xiaoyun（Windows 原生桌宠）
> 结论口径：以「可交互实时性」为第一约束，区分**实时回路**与**离线资产生产线**两条链路。

---

## 0. 结论摘要（先看这 5 条）

1. **对话层已商品化，壁垒不在模型。** 2026 年主流产品的差距集中在三件事：分层记忆、主动性、形象一致性。模型本身用免费池/中杯模型即可达到「像人」的下限。

2. **形象驱动存在四个代际，本机只能落在 G2。** G1 立绘/Live2D、G2 3D VRM 程序化驱动、G3 生成式视频表演、G4 实时神经数字人。8GB 显存 + 16GB 内存的硬约束下，G3 与 G4 均不可能进入实时回路，**只能作为离线资产生产线**。

3. **最重要的一条工程判断：不要让扩散模型进入实时回路。** 让 MiniMax H3 / Seedream 在后台批量产出「动作库、表情贴图、立绘、三视图」，实时回路仍由确定性代码（骨骼、blendShape、表情权重插值）驱动。这既绕开了延迟与显存，又正好复用你已有的 ComfyUI 资产。

4. **小芸的记忆架构已越过「猫箱级」，接近「星野级」骨架。** 已有的 FTS5 + bigram + 向量 + mem0 式四操作消解，在结构上强于多数开源伴侣项目；真正的缺口是**关系状态（attitude/affinity）与事实的时间维度（有效期、失效）**。

5. **情绪链路是当前最大的「低成本高收益」改造点。** 现状是「回复文本 → 关键词计票 → 只调 TTS 语速/音调」，属后验推断、单向下行、不触达面部。改成「模型结构化输出情绪 → 独立通道下发 → 同时驱动 TTS 参数 + VRM 表情 + 身体微动作」，投入约 2–3 人日，观感提升显著。

## 2. 通用技术架构（六层）

业界方案无论开源商业，拆开都是同一套六层结构，差异在每层的实现深度。

```
L6 主动性/情境     定时唤醒、屏幕感知、事件驱动、关系阶段推进
L5 形象与驱动      Live2D | VRM | 2.5D视频 | 神经数字人
                   ├ 口型(viseme/音量包络) ├ 表情(blendShape) ├ 动作(骨骼/程序化) ├ 视线
L4 语音             VAD → ASR → (打断/barge-in) → TTS(流式/克隆/情感)
L3 记忆             工作记忆(上下文) → 情景记忆(事件) → 语义记忆(事实) → 关系状态
L2 对话编排         人格注入、模型路由、流式、工具调用、输出结构化
L1 人格设定         system prompt / 角色卡 / LoRA 微调 / 边界与拒答策略
```

### 2.1 L1 人格设定

三种做法，成本与稳定性递增：

| 做法 | 说明 | 稳定性 | 适用 |
|---|---|---|---|
| 纯 system prompt | 一段人设文本 | 低（长会话漂移） | 原型 |
| 角色卡（SillyTavern 格式） | 人设 + 示例对话 + 世界书 + 开场白，可被社区复用 | 中 | 多角色生态 |
| LoRA / SFT 微调 | 把语气、边界、反应模式写进权重 | 高 | 单角色深度产品 |

> 主流平台实际是「角色卡 + 大模型 + 一致性约束」三层兜底，而非微调。微调的主要代价是**模型升级即失效**，对个人项目不划算。**建议小芸维持「人设 JSON + 示例对话 + STAGE_HINT 格式约束」路线，把预算投到记忆与表现层。**

### 2.2 L2 对话编排

2026 年的工程共识：

- **流式是默认项**：首 token 延迟决定体感，非总时长；
- **双通道输出**：文本通道给人看/给 TTS，结构化通道（情绪、动作意图、记忆写入指令）走旁路，不进 TTS 文本；
- **打断（barge-in）**：ASR 检出人声即停止 TTS 播放并撤销未播队列；
- **模型路由**：按任务分层（闲聊/工具/记忆抽取/情绪判定可用不同模型），这是成本与延迟的主要杠杆。

> 这一层与你现有的 `or_proxy`（多模型注册表 + 优先级回落）+ `_publish_reply` 唯一发声出口的设计**已经同构**，属领先项。

### 2.3 L3 记忆（差异化最大的一层）

业界已从「上下文窗口 + 摘要」演进到**四层记忆**：

| 层 | 内容 | 存储 | 检索 |
|---|---|---|---|
| 工作记忆 | 最近 N 轮原文 | 内存 | 直接拼进 prompt |
| 情景记忆 | 「某天发生了什么」 | 事件表 + 时间戳 | 时间窗 + 语义 |
| 语义记忆 | 「她/他是什么样的人」 | 事实库（结构化 + 向量） | 混合检索 |
| 关系状态 | 亲密度、当前态度、未解心结 | KV / 单行状态 | 常驻注入 |

商业产品的分野正好在这一层：

- **Character.AI**：长期靠长上下文 + 用户手写 memory box；2026-04/05 才上线 Story Memory / Facts / Lorebook，属「补课」。
- **Replika**：结构化用户档案 + 日记式自省，但**不可见、不可控**，且随模型更新漂移。
- **星野**：分层存储 + 向量检索，记忆用于**驱动角色成长**（生日/禁忌/偏好影响后续行为）。
- **猫箱**：会话级缓存 + 轻量检索，**保障会话内不崩人设**，不改变长期行为。

> 一句话概括差异：**星野的记忆是状态机，猫箱的记忆是缓存。** 小芸当前的结构（事实库 + 向量 + 画像 profile）已具备状态机的地基，缺的是「状态转移规则」。

### 2.4 L4 语音

链路固定为 `VAD → ASR → LLM → TTS(流式) → 播放`，工程难点全在时序：

- **尾点判定**：静音多久算说完（阈值过低会自听循环，过高会截断）；
- **打断**：用户开口时 TTS 必须能被抢占，且已入队未播的音频要撤销；
- **播放态上报**：前端必须持续上报「还在播、播到第几段」，否则后端会误判空闲并叠加新语音——**这是最容易踩的坑，你已用 SEQ/PLAYBACK 三件套解决**；
- **情感控制**：三条路线——参考音频驱动（GPT-SoVITS）、文本指令驱动（CosyVoice3「用低声说」）、情绪标签（Fish Speech `[sigh]`、MiniMax `(chuckle)`）。

### 2.5 L5 形象与驱动（见第 6 节选型）

### 2.6 L6 主动性

从「被动应答」到「主动开口」是伴侣感的关键跃迁，实现要素：

- **触发器**：定时（久未互动/深夜/清晨）、事件（前台窗口变化、系统状态）、状态（关系值、未完成话题）；
- **门控**：打扰成本模型，工作态压制、专注态降频；
- **话术生成**：不能是模板播报，需要带情境上下文的一次生成（你已有 `_speak_proactively` + `context_engine`，属正确实现）。

## 5. 关键子系统选型对比

### 5.1 TTS

| 方案 | 部署 | 首包延迟 | 克隆样本 | 情感控制 | 许可 | 本机可行性 |
|---|---|---|---|---|---|---|
| **豆包 seed-tts 2.0（现状）** | 云 | 低（流式 PCM） | 音色库 + 定制 | 有限（`emotion`/`speech_rate` 字段，实际可用度需实测） | 商用需授权 | ✅ **已跑通，维持** |
| **CosyVoice 3** | 本地 | 流式最低约 150ms | 3s 零样本 | **文本指令控情感**（"用低声说"） | Apache-2.0 | ⚠️ 吃显存，与 Hunyuan3D 冲突 |
| **GPT-SoVITS v2Pro** | 本地 | RTF≈0.03（4060Ti） | 5s 零样本 / 1min 微调 | 靠参考音频带情绪 | MIT | ⚠️ 需常驻 ~2–3GB |
| **Fish Speech S2** | 本地/云 | 流式 | 10–30s | **1.5 万情绪标签** | 非商用 | △ 许可不适合 |
| **IndexTTS-2.5** | 本地 | RTF≈0.21 | 单参考克隆 | **8 维情绪向量 + 音色/情感解耦** | 需授权 | △ 延迟偏高 |
| **MiniMax speech-2.8（已接）** | 云 | 中 | 音色库 | **`emotion` + `(sigh)/(chuckle)` 标签** | 商用 | ✅ **已在代码中，可作情感增强备选** |

> **结论**：小芸已同时具备豆包（默认）与 MiniMax（情感标签）两条云通道，**本地 TTS 不建议引入**——8GB 显存要留给视觉与未来动作模型，且本地 TTS 常驻会与桌宠「随时在线」的资源预算冲突。
> **改造点不是换引擎，而是让情绪信号真正流到引擎**（见 §8）。

### 5.2 记忆方案

| 方案 | 形态 | 检索 | 时间维度 | 接入成本 | 对小芸适配 |
|---|---|---|---|---|---|
| **mem0** | 外置记忆中间件，`add/search` | 向量优先，可选图 | 弱（矛盾消解但不保时间线） | 低 | ✅ 思路已内化（四操作消解） |
| **Memobase** | **用户画像型**记忆 | 画像 + 事件 | 中 | 中 | ★ **最贴合伴侣场景** |
| **Zep / Graphiti** | 图原生 + 双时间轴 | 语义+全文+图遍历 | **强**（旧边失效、历史可查） | 高（需图库） | △ 过重 |
| **Letta (MemGPT)** | 带记忆的 Agent 运行时 | 分层 + 自编辑块 | 弱（依赖 agent bookkeeping） | 高（须接受其 runtime） | ✗ 与现有 Flask 架构冲突 |
| **自研 memory_store（现状）** | SQLite FTS5 + bigram + 向量 + profile | 混合 | **无** | — | ✅ 已够用，补两列即可 |

> **注**：SQLite FTS5 对中文默认分词无效，必须 bigram 索引——小芸已处理，这一点多数开源项目仍在踩坑。
> **结论**：不引入外部记忆框架。**在现有表上补 `valid_from / valid_to` 与 `attitude` 两个维度，成本最低、收益最直接。**

| 路线 | 表现力 | 工程量 | 实时性 | 资源 | 一致性 | 结论 |
|---|---|---|---|---|---|---|
| **G1 Live2D** | 中高（2D 表现力强，微表情靠参数） | 中（需分层 PSD + 绑定） | 优 | 极低（CPU） | 优 | 备选：若想要 2D 观感 |
| **G2 VRM 3D** | 中（受 VRM 预设表情限制） | 低（已有管线） | 优 | 中（GPU 5–15%） | 优 | ✅ **当前正确选择** |

| **G4 实时神经数字人** | 极高 | 极高（需服务端 GPU 集群） | 优（<1.5s） | 不可行 | 高 | ✗ 本机排除 |

### 5.4 表情与动作驱动

**VRM 1.0 的表情词汇是硬限制**：预设仅 `happy / angry / sad / relaxed / surprised` + `blink / lookAt` + 5 元音 viseme。这与「傲娇、吃醋、心疼、敷衍」这类细腻情绪不匹配——**这是小芸当前观感的天花板**。

三条突破路径（按性价比排序）：

1. **程序化微表情叠加（零美术成本，首选）**：在已有表情权重上叠加眉毛/眼睑/头部微动/呼吸/重心偏移，用确定性代码实现。业界桌面宠物普遍靠这一层「活起来」，而非依赖更多 blendShape。
2. **自定义 expression（需改模型，你有管线优势）**：VRM 1.0 支持 custom expressions。你的模型由 Hunyuan3D + Blender 自产，**可以在 Blender 里直接加 ShapeKey 并导出为自定义表情**——这是普通用户做不到、而你独有的路径。
3. **ARKit 52 blendshape 映射（上限最高，成本最高）**：需要模型具备 52 通道，且需自动生成方案（已有论文级方法处理「多部件动漫脸」）。适合作为长期目标。

**动作层**：
- 程序化 idle（呼吸/摇摆/重心）——必须有，成本最低；
- 预录动作库（VMD / VRMA）——`VRMA` 是 three-vrm 生态的标准格式，可直接接 `AnimationMixer`；
- 生成式动作（HY-Motion 1.0 / Kimodo）——文本→SMPL，需 retarget，精度与工程量中等；
- 视频→动作（GVHMR/WHAM → SMPL → VRM）——**实测精度有限**（有公开实践在舞蹈素材上 MP 相似度仅约 39/100），适合做「标志性动作」而非批产。

### 7.2 四条生产线（全部离线，不进实时回路）

**线 A′：角色形象生产 —— 参数化建模 + 生成式贴图（替代原「三视图 → 图生 3D」）**

> **原线 A 已废弃（2026-11-04 决定）**。原因是结构性的，不是调参问题：
> 1. **三视图不是真正的 3D 投影**——AI 出图每张独立采样，正/侧/背的剪影、五官高度、衣褶走向互不自洽，重建模型只能从「互相矛盾的 2D」里猜体积 → 五官浮肿、鼻梁塌陷、手指粘连；
> 2. **动漫比例是画法约定，不是物理体积**——大眼、细颈、硬边衣褶、纸片裙摆违背人体先验，单视图重建会按真人比例「纠正」回去，越还原越难看；
> 3. **容量与分辨率双重不足**——2mini 是轻量档、输入约 512 级，发丝/眼睫/服装层次在 mesh 阶段已丢，stageT 贴图只是把错误几何刷上颜色，救不回来。
>
> 换更大的图生 3D 模型（2.1/preview/Tripo/Rodin）只能缓解，不改变「从 2D 猜 3D」这一根本矛盾。**结论：瓶颈在几何，不在贴图。**

```
【几何：确定性】VRoid Studio（已装）
  ├ 参数化捏人：脸型 / 眼型 / 眉 / 鼻 / 口 / 体型
  ├ 载入 Booth 服装素材（booth_dl/JK制服*、vroid_items/）→ 直接穿戴
  ├ 发型用 VRoid 发型编辑（或导入手工发型 mesh）
  └ 导出 .vrm → 骨骼 / 弹簧骨 / UV / 14 预设表情 全部自动合规
        ↓
【表面：生成式】Blender 4.5.9（只做加法，不重建网格）
  ├ 贴图重绘：Seedream 出服装/妆容图 → 投影到现有 UV（AI 真正擅长的环节）
  ├ 加 ShapeKey → VRM 插件注册为 custom expression（傲娇/害羞/困/敷衍）
  └ 发型/服装 mesh 微调 → 重导（不动骨架）
        ↓
fix_vrm_restpose.py（仅改骨骼后需要）→ SKIN_TINT_TABLE 标定 → 入库
```

**核心原则：几何走参数化（确定性），贴图走生成式（AI 长处）。** 原线 A 的错误是让 AI 干了它最不擅长的几何，而不是表面。

**已验证事实（2026-11-04 直接解析 GLB）：**

| 文件 | 版本 | 预设表情 | custom | 弹簧骨 | 判定 |
|---|---|---|---|---|---|
| `小芸.vrm` | VRM 1.0 | 14 | **0** | 24 | VRoid 导出签名 |
| `小芸-jk.vrm` | VRM 1.0 | 14 | **0** | 26 | VRoid 导出签名 |
| `vroid_ref/AvatarSample_E.vrm` | VRM 1.0 | 14 | 0 | — | VRoid 官方示例 |

- 14 个预设固定为 `happy / angry / sad / relaxed / surprised / aa / ih / ou / ee / oh / blink / blinkLeft / blinkRight / neutral`，其中 `blinkLeft/blinkRight/neutral` 是 VRoid 的固定签名 → **现有小芸资产本来就出自 VRoid，这条路过一次且成功**；
- **custom 表情数为 0**：VRoid 只导出 14 个预设，导不出自定义表情。→ 想要「傲娇/吃醋/害羞/敷衍」这类细腻情绪，**必须走 Blender 加 ShapeKey 并注册为 custom expression**，这一步绕不过（对应 §5.4 路径 2）；
- 因此表情工作分两步：先做**运行时组合**（5 预设加权混合 + 头部倾斜 + 视线 + 呼吸，零资产成本），确认哪几个情绪确实表达不出来，再只为这几个去 Blender 雕 ShapeKey，避免无效返工。

**两条路线的产物结构对比（`tools/check_vrm.py` 实测，2026-11-04）：**

| 指标 | 小芸.vrm（VRoid） | bjd3d_v3 / luna.vrm（图生 3D） |
|---|---|---|
| 节点数 | 150 | **20** |
| 网格 / 图元 | 3 / 14 | 1 / 1–6 |
| humanoid 骨骼 | 54 根，含 `leftEye/rightEye` | **缺双眼骨 → 目光追随直接失效** |
| 弹簧骨 | 24 组 | **0 组 → 头发/裙摆完全不动** |
| 自检结论 | **可部署** | **不可部署** |

> 这张表解释了「观感差」的真正来源：不只是长相，而是**生成式产物没有手指骨、没有眼骨、没有弹簧骨**。19 骨绑定是「能站能挥臂」的下限，而「像活人」需要的恰恰是眼球、指节、发丝这三层细节——它们在 mesh 阶段就不存在，后续任何贴图或调参都补不回来。**这不是模型大小的问题，是拓扑与骨骼拓扑的问题。**

**入库自检工具已就绪**：`project-nn/xiaoyun/tools/check_vrm.py`，纯标准库、无依赖，任何新 VRM 部署前必跑：

```bash
python tools/check_vrm.py 小芸.vrm            # 人读格式
python tools/check_vrm.py *.vrm --json        # 机读，可接启动脚本
```

检查 8 项：版本、预设表情（缺 `aa/ih/ou/ee/oh` 会让 `driveMouth` 静默失效）、自定义表情、humanoid 骨骼（缺眼骨会让目光静默失效）、弹簧骨、节点缩放（非 1.0 即 FAIL，对应铁律禁区）、绑定姿态包围盒、网格规模。FAIL 阻断部署，WARN 仅提示。

**线 B：表情差分（用于美术参考与 2D 备选，不直接驱动 VRM）**
```
已有立绘 → 参考图生图(Seedream reference_images) + 固定 seed/提示词骨架
  → 6–8 张表情差分（喜/怒/哀/惊/羞/困/嫌弃/敷衍）
```
用途：① 作为 §5.4 程序化微表情的**目标参考**（照着调参数，比盲调快）；② 作为 Blender 里雕 ShapeKey 的**对照图**（线 A′ 第三步）；③ 若未来切 Live2D，直接作为差分素材。
**不要**指望差分图能驱动 3D 模型——两者不是同一套参数空间。

**线 C：动作生产线（最高价值）**
```
参考舞蹈/日常动作视频
  → H3_V2V 骨架跟随(DWPose) 生成「小芸体型」动作视频   [ComfyUI]
  → GVHMR/WHAM 提取 SMPL（RTX 4080 实测 300 帧约 52s，峰值 4.2GB）[本地 GPU]
  → retarget SMPL → VRM humanoid 骨架 → 四元数连续性修正
  → 导出 .vrma → 挂到 desktopvrm.html 的 AnimationMixer
```
- 直接用 `H3_换人_通用模板_209帧_骨架门控.json` 出「小芸版」素材，再提动作，比从原片提动作更贴合体态；
- 精度预期：**标志性动作可用，复杂舞蹈会穿模**（公开实践显示舞蹈类相似度上限受提取器精度限制）；建议先做 5–8 个高频动作：招手、点头、歪头、伸懒腰、转身、坐下、比心、打哈欠。

**线 D：2.5D 表演层（低成本高观感的备选）**
```
I2V 8step turbo → 3–5s 循环（呼吸 idle / 说话 / 害羞 / 生气）
  → 抠像 + 循环接缝处理 → 前端 <video loop muted> 或帧序列
```
用途：作为 VRM 的**补丁层**——在特定情绪（害羞、生气）时短暂切换到预渲染片段，制造「表现力爆发」。风险：切换会有跳变，只适合「表情特写」而非全身。

### 7.3 必须遵守的本机约束

| 约束 | 值 | 违反后果 |
|---|---|---|
| 宽高整除 | **必须能被 32 整除** | `patchify_video` shape 报错 |
| 帧数 | `length % 17 == 5`（如 81/121/209） | 采样器报错 |

## 8. 集成方案（分三期，带具体改动点）

### 一期：打通「情绪 → 语音 + 表情」链路（P0，约 2–3 人日）

**问题**：现在 `_detect_emotion(text)` 在 TTS 前做关键词计票，只影响 `rate/pitch`；VRM 页的表情只由 poke/感知触发，两条链路互不相通。

**方案**：情绪改为**模型结构化输出 + 旁路下发**，禁止写进 TTS 文本（`STAGE_HINT` 已明令禁止括号内容，且 TTS 会念出来）。

```
LLM 输出 → 两段
  ├ 纯台词（进 TTS，保持现有 _strip_stage_text 兜底）
  └ EMOTION 旁路：{"emo":"shy","intensity":0.7}
        ↓
   _publish_reply()  ← 唯一发声出口，在此处统一广播
        ├→ tts_stream.stream_pcm(..., speech_rate=映射表[emo])
        └→ SSE/轮询事件 {"emo":..., "intensity":...} → 前端 __xyFrameHook 消费
```

落地要点：
1. `xiaoyun_server.py:490` `STAGE_HINT` 增加一行：要求输出末尾以独立行给出 `[[emo:xxx,0.7]]`；
2. `_strip_stage_text()`（行 503）在剥离括号前**先抽取该标签**并存入本轮 payload，再清洗；
3. `_publish_reply()`（行 1878）把 `emo/intensity` 写进 `/api/last` 与事件流；
4. `pages/desktopvrm.html:2019` 的 `expressionManager` 写入点改为读 `emo`，并在 `window.__xyFrameHook`（行 2115）里按 `intensity` 做**插值过渡**（不要瞬切，瞬切会「面瘫跳变」）；
5. `_EMOTION_RULES` 保留作**兜底**（模型漏标时用），不删除。

> 注意：不要复用 `/api/poke` 那种「seq 变化触发一次」的机制——情绪是**持续态**，需要目标值 + 平滑，而非一次性事件。

### 二期：记忆升级为「状态机」（P1，约 3–4 人日）

1. `memory_store` 增列：`valid_from / valid_to / confidence`（SQLite `ALTER TABLE` + 迁移函数，已有 `_migrate()` 位置）；
2. `memory_store.set_profile / get_profile` **已有**，直接扩展键：`affinity`（0–100）、`attitude`（当前态度词）、`open_loops`（未完成话题，JSON）；
3. `memory_brain` 四操作增加一路「关系更新」：每 N 轮根据事件情感极性微调 `affinity`，并写入 `memory_events`；
4. `context_engine.build_context()` 注入顺序改为：`关系状态 → 画像 → 相关事实 → 近期事件`（顺序影响模型权重，关系状态必须靠前）。

> 这一步之后，「她记得你」会升级为「她对你的态度因你而变」——这是星野与猫箱的本质差异，也是留存主因。

### 三期：表现力与资产闭环（P2，按需）

1. **程序化微表情层**：在 `__xyFrameHook` 内叠加呼吸、重心摇摆、眉毛/眼睑次通道，与 `emo` 解耦（即使情绪不变也在动）；
2. **VRMA 动作库**：`/api/motions` 扩展支持 `.vrma`，走线 C 生产；
3. **自定义 expression**：Blender 内加 ShapeKey（`shy / annoyed / sleepy / pout`）→ 导出 custom expression → 前端按名调用，绕开 VRM 预设限制；
4. **形象入库自检脚本化**：不写「从三视图生成模型」的脚本（已废弃），改写 **`check_vrm.py`**（**已完成**，见 §7.2）——入库前校验：① 是否 VRM 1.0；② 14 预设表情是否齐全；③ 弹簧骨数量与命名；④ humanoid 骨骼映射是否完整（含 `leftEye/rightEye`，缺失会导致目光追随静默失效）；⑤ 包围盒高度与缩放是否为 1.0（缩放模型是铁律禁区）；⑥ rest pose 是否已修正。任一项不过则拒绝部署。

## 9. 延迟与性能预算

桌宠体感的真实指标是**「说完话 → 她开口」**，不是 TTS 总时长。

| 环节 | 现状（估） | 目标 | 优化手段 |
|---|---|---|---|
| ASR 尾点判定 | 400–700ms | 350ms | 动态静音阈值 + 语义尾点 |
| LLM 首 token | 300–900ms | ≤500ms | 短 prompt、小模型兜底、禁用长思考 |
| TTS 首包 | 200–400ms | ≤250ms | 豆包流式（已具备） |
| 前端首帧口型 | 50–120ms | ≤80ms | 预建 AudioContext、首帧预解码 |
| **合计** | **约 1.0–2.1s** | **≤1.2s** | 关键在 LLM 首 token |

> 结论：**不要为了「更强的模型」牺牲首 token**。人设一致性靠记忆注入，不靠模型参数量。

## 11. 风险与合规

1. **依恋风险**：伴侣型产品的主要伦理争议集中在「回避型使用」。设计上应保留「不迎合」能力（人设有边界、会拒绝），避免无条件顺从——这同时提升长期可信度。
2. **内容边界**：本地自用无对外服务义务；若未来分发，生成式服务需按境内规定做安全评估与内容过滤。
3. **数据本地性**：小芸全本地（SQLite + 本地模型）是结构性优势，云端方案（含记忆）会引入隐私与合规成本，**不建议为了「更强记忆」上云**。
4. **模型漂移**：切换对话模型会导致人设语气漂移（Replika 的历史教训）。建议**人设回归测试集**：固定 30 条探针问题，换模型后跑一遍比对语气与边界。

## 附录 B：AI 直播（互动 / 动作 / 唱歌）实现拆解

### B.1 两条互斥的技术路线

| 路线 | 代表 | 原理 | 算力门槛 | 个人可行性 |
|---|---|---|---|---|
| **A 资产 + 参数驱动** | Neuro-sama、AIRI、个人 AI 主播 | 模型 + LLM + TTS + 动作库，渲染确定性 | 单机 | ✅ |
| **B 端到端生成式数字人** | 虎牙 VAM 1.0（2026-07） | DiT 直接出帧，音频条件驱动口型动作 | **8×H200 达 36.4fps** | ✗ |

> VAM 1.0 公开指标：480×832 / 28fps / 首帧 1.3s / 后续帧 0.77s / 连续 24h 不漂移。三阶段训练＝多参考图锚定身份 → DPO 平衡口型表情动作 → 蒸馏 20 步压到 4 步，外加自纠错防累积误差。**这条路的技术含量在「不崩」，不在「能生成」。**

### B.2 各能力的真实性

| 能力 | 是否实时 | 实现方式 |
|---|---|---|
| 弹幕互动 | ✅ 实时 | 平台 WebSocket → 队列限流 → LLM |
| 语音 | ✅ 实时 | 流式 TTS，边合成边播 |
| 口型 / 表情 | ✅ 实时（权重驱动） | 音频包络 + 音素 → viseme；情绪标签 → blendShape |
| **动作** | ⚠️ 实时播放，**资产预生成** | 动作库（VMD/VRMA/FBX）+ 标签触发 + 与 idle 叠加 |
| **唱歌** | ❌ **离线渲染** | SVS 出干声 → RVC 换声 → wav；直播时播放 + 口型跟随 |

### B.3 唱歌三件套

```
歌词 + 曲谱 → 歌声合成(SVS) → 换声(RVC) → 混音 → wav
                                            ├→ 直播播放（伴奏轨并行）
                                            └→ 能量包络 + 谱通量 onset → viseme
```

- **SVS**：DiffSinger（开源可训中文）、ACE Studio / Synthesizer V（商业，质量最好）、NNSVS；
- **换声**：RVC（开源，数十分钟素材即可）、so-vits-svc（较老）；
- **口型**：**不需要字级时间戳**——用能量包络 + onset 锚定即可，`lipsync.js` 现有方案直接复用，只要把输入从 TTS 音频换成歌曲音频；
- **必须离线**：SVS 自回归推理不是实时量级，直播现场合成一定断。

### B.4 动作三件套

1. **库**：VMD（MMD，PMX 页已有）/ VRMA（VRM 标准）/ FBX；
2. **触发器**：礼物（特定礼物→特定动作）、弹幕关键词、整点、情绪档位；
3. **叠加**：idle 基础层 + 手势 additive 层 + 表情层，三层各自权重，不能整段替换（会僵）。

### B.5 直播特有的六个工程问题（比技术选型更致命）

| 问题 | 说明 |
|---|---|
| 队列与限流 | 弹幕 100 条/分钟不能逐条回；需优先级（礼物 > 提问 > 闲聊）+ 聚合 + 丢弃策略 |
| 冷场 | 无互动时需自主话题（`context_engine` 的 idle 意图池正好是为此设计） |
| 复读 | 长跑必现（你已用 `_PROACTIVE_SAID` 去重池解决，可直接搬） |
| 内容安全 | 输入过滤防「被教坏」+ 输出审查 + 兜底话术，双向 |
| 长跑稳定 | 显存回收、贴图缓存刷新、看门狗重启、断流重连 |
| 成本 | TTS 按字计费；8 小时直播 × 每分钟数句 → 必须做预算上限 |

### B.6 小芸的复用矩阵

| 环节 | 现状 | 结论 |
|---|---|---|
| LLM 路由 | `or_proxy` 多模型 | ✅ 直接用 |
| 流式 TTS | 豆包 PCM | ✅ 直接用 |
| 口型 | `lipsync.js` | ✅ 直接用（唱歌同源） |
| 主动话题 | `context_engine` | ✅ 直接用（冷场即主动性） |
| 复读抑制 | `_PROACTIVE_SAID` | ✅ 直接用 |
| 表情 | VRM 5 预设 | ⚠️ 够用但粗 |
| 动作 | `/api/motions` 仅 PMX 页 | ⚠️ 需扩到 VRM + `.vrma` |
| 弹幕接入 | 无 | ❌ 新增（B 站开放平台 WebSocket） |
| 渲染输出 | 桌面透明窗 | ❌ 新增（OBS 虚拟摄像头 / Spout2） |
| 守护 | 单实例锁，无看门狗 | ❌ 新增 |

> **⚠️ 最关键的风险：直播会污染小芸的记忆。** 现有记忆是「我和主人的私密关系」，直播是「我和几百个观众」。若不分片，她会在直播里说出你的私事，也会把观众的玩笑记成你的偏好。**上直播前必须先做记忆分区（`scope: private / stream`），这是前置条件，不是优化项。**

### B.7 建议落地顺序

1. **本地模拟**：stdin/文件模拟弹幕源 → 队列限流 → 复用现有 LLM+TTS+口型，不接平台、不推流；
2. **画面输出**：OBS 虚拟摄像头捕获 VRM 页 → 私密推流验证稳定性；
3. **动作与唱歌**：VRMA 动作库 5–8 个 + 1 首歌离线渲染并口型对齐；
4. **记忆分区 + 内容审核**；
5. 最后才接平台弹幕与公开推流（合规标识、实名、内容安全）。
