## 0. 一句话结论

方舟能用的东西比控制台显示的少，而且**两把 Key 的权限是按模型逐个授予的，不是按产品线分的**：

| 类别 | 可用 | 走哪把 Key | 端点 | 实测 |
|---|---|---|---|---|
| 语言 | 18 个对话模型（含角色档） | 普通 | `/v1/chat/completions` | 435–6513ms |
| 视觉理解 | 同 18 个里的多模态档 | 普通 | `/v1/chat/completions` | 1455ms，看图准 |
| 视觉生成 | 5.0 pro/flash（Plan，8s）＋ **4.0（普通，4s）** | Plan / 普通 | `/v1/images/generations` | 4–15s/张 |
| 语音合成 | `seed-tts-2.0` + 15 个音色 | **Plan** | openspeech HTTP | 0.6–1.4s |
| 语音识别 | **`seed-asr-2.0`（WS 独立模型）** | **Plan** | openspeech **WebSocket** | 1.16s |
| 向量 | 只有 1 个多模态；文本向量**控制台已开通但仍调不到** | 普通 | `/v1/embeddings` | 206–327ms |
| 视频 | 只有 1.0-pro-fast | **普通** | `contents/generations/tasks` | 任务式 |
| 3D | seed3d-2.0 / hyper3d-gen2 / hitem3d-2.0（**仅图生 3D**） | **普通** | `contents/generations/tasks` | >4min |

四个最容易踩反的：**生图 5.x 要 Plan Key，4.0、视频、3D 要普通 Key**；**语音识别有独立 WS 端点，只是不在方舟 `/api/v3` 下**；**文本向量控制台「已开通」≠ REST 可调**；**3D 只吃图，纯文本提交能过校验但任务必失败**。

## 3. 向量模型（1 个可用）

| 项目 | 值 |
|---|---|
| 模型 | `doubao-embedding-vision-251215` |
| 端点 | `POST /api/v3/embeddings/multimodal` |
| 维度 | **只支持 1024 或 2048**（1536/768/512/256 全部 400） |
| 输入 | text / image_url / video_url 任意混合 |
| 延迟 | 2048 维 219ms、1024 维 327ms |
| 同空间 | 文本与图像 cos ≈ 0.42，**可跨模态检索** |

```json
{"model":"doubao-embedding-vision-251215",
 "input":[{"type":"text","text":"小芸在写代码"}],
 "dimensions":1024,
 "sparse_embedding":{"type":"enabled"}}
```

返回 `data.embedding`（稠密）+ 可选 `data.sparse_embedding`（稀疏，11 条）+ `data.multi_embedding`（开多向量时 64 条 token 级向量）。

**三个反直觉点**：

1. **纯文本向量模型：控制台显示「已开通」，但 REST 调不到**。2026-11-05 00:40 复核时控制台里 `Doubao-embedding` / `Doubao-embedding-large` / `Doubao-embedding-vision` 三款均为「已开通 / 剩 50 万 tokens」，但实测 **4 族 × 12 个日期版本 = 48 个候选 ID 全部 404**，两种 Key、`/api/v3` 与 `/api/plan/v3` 都试过（后者返回 `UnsupportedModel`）。说明额度在控制台侧已生效，但外部 REST 还不能直调——大概率需要先建「推理接入点」（`ep-` 开头）才能用。
   实际做文本检索仍只能用多模态模型的 text 输入：能用，但单条请求。
2. **多段 input 只返回一条融合向量**（`data` 是 dict 不是 list），不是 batch。要 N 条就得发 N 次，每次约 220–330ms。
3. **`dimensions=1024` 是刻意选的默认值**。项目现网 `memory_store` 用 Ollama `bge-m3`（1024 维），方舟降维到 1024 后**向量库可直接换后端、不用 `purge_mismatched_vectors` 重建**；要原生 2048 必须显式传参。

### 4.2 语音识别（ASR）

**有独立模型，但只走 WebSocket**（不在方舟 `/api/v3` 下，所以 `/audio/transcriptions` 是 404，与「没有能力」是两件事）。

| 项目 | 值 |
|---|---|
| 模型 | `doubao-seed-asr-2.0` |
| 资源 ID | **`volc.seedasr.sauc.duration`**（注意是 `seedasr`，不是 `bigasr`；小时版。并发版为 `…sauc.concurrent`） |
| 端点 | `wss://openspeech.bytedance.com/api/v3/plan/sauc/bigmodel_nostream`（准确优先）<br>`wss://openspeech.bytedance.com/api/v3/plan/sauc/bigmodel_async`（边发边出） |
| 鉴权 | **Plan Key**；普通 Key 握手阶段报 `acquire failed ... status code:401` |
| 音频 | wav / 16bit / 单声道；**16k 与 24k 都接受**（按 `audio.rate` 声明） |
| 延迟 | 3.2s 音频约 1.16s；6s 音频约 1.16s（几乎不随长度增长） |

协议是二进制帧，不是 JSON：`4 字节头 + seq(int32) + payload_len(uint32) + gzip(payload)`。首帧 `CLIENT_FULL_REQUEST(0b0001)` 描述音频格式，之后每帧 `CLIENT_AUDIO_ONLY(0b0010)`，最后一帧 seq 取负并把 flags 置 `NEG_WITH_SEQUENCE(0b0011)`。已封装进代理的 `_asr_ws()`，不需要自己写。

**两条路线对比**（同一个 wav，各 5 次取中位）：

| 音频长度 | WS 流式 | chat + `input_audio` | 差距 |
|---|---|---|---|
| 6.0s | **1163ms** | 1685ms | WS 快 31% |
| 0.6s | **678ms** | 946ms | WS 快 28% |

回落路线仍保留（`backend=chat` 可强制）：把音频塞进多模态对话，`content` 里用 `input_audio`，模型 `doubao-seed-2-0-mini/lite-260428`；`audio_url` 形式会被拒。

```bash
# 走代理：默认 ws，非 wav 或失败时自动回落 chat
curl http://127.0.0.1:8787/v1/audio/transcriptions \
  -H "Authorization: Bearer local" -H "Content-Type: application/json" \
  -d '{"audio":"D:/path/a.wav","language":"zh"}'
# → {"text":"…","model":"seed-asr-2.0","backend":"ws","latency_ms":1163}
```

> 注意：`backend=ws` 只吃 **wav/16bit/单声道**。mp3 会直接走 chat 路线，不会报错。

| `doubao-seedance-1-0-pro-fast-251015` | **200** | 404 UnsupportedModel | 视频只有这一档，走普通 Key |
| `doubao-seed3d-2-0-260328` | **200** | 404 UnsupportedModel | 3D 走普通 Key |
| `hyper3d-gen2-260112` / `hitem3d-2-0-251223` | **200** | 404 UnsupportedModel | 第三方 3D，同样走普通 Key |

### 5.1 Seedream 4.0：比 5.0-flash 快一倍，且不占 Plan 额度

| 项目 | 4.0（普通 Key） | 5.0-flash（Plan） |
|---|---|---|
| 1K 文生图 | **4.1–4.6s** | 7.6–8.3s |
| 尺寸 | `1K`/`2K`/`4K` 或 `1024x1024`/`2048x2048`/`4096x4096` | 同左 |
| 参考图 | `image`（单图）/ `images`（多图），**没有 `reference_images`** | `reference_images` |
| 返回 | `url` 或 `b64_json` 均可 | 同左 |

两条容易踩的：**`768x1024` 这类自定义宽高会 400**（只认 1K/2K/4K 档位或该档的整数尺寸）；**参考图字段名两边不同**，写错不会报错，只会当成纯文生图跑——代理已按后端自动切换字段。

### 5.2 3D：只能图生，且很慢

三款（`doubao-seed3d-2-0-260328`、`hyper3d-gen2-260112`、`hitem3d-2-0-251223`）**都必须提供图片**：

- 纯文本提交 → 任务 `200` 拿到 id，随后 `failed: InvalidParameter (body -> image_data / Either images or …)`
- 传图（`content` 里 `{"type":"image_url","image_url":{"url": dataURI}}`）→ 任务正常跑，但 **>4 分钟仍在 running**
- 计费按 tokens：seed3d 0.08 元/千 tokens、hyper3d 0.06、hit3d 0.08（并发 3–30、RPM 60–600）

视频与 3D 都是**任务式**：提交后拿 `id`（如 `cgt-20261105005108-kvrf6`），再 `GET /api/v3/contents/generations/tasks/{id}` 轮询。代理只做了生图的一步式封装。

## 6. 代理新增了什么

改了 `project-nn/or_proxy/or_proxy.py`（累计 +约 420 行）：

| 新增 | 说明 |
|---|---|
| `POST /v1/embeddings` | OpenAI 兼容，内部转 `/embeddings/multimodal`；默认 `dimensions=1024`；透传 `sparse_embedding` / `multi_embedding` / `instructions` / `encoding_format` |
| `POST /v1/audio/transcriptions` | **首选 WS 流式 ASR（约快 30%）**，非 wav/失败时自动回落 chat `input_audio`；`backend=ws\|chat` 可强制 |
| `_asr_ws()` / `_wav_info()` | 方舟流式 ASR 的二进制协议封装（gzip 帧、seq 负数收尾），约 110 行 |
| `POST /v1/audio/speech` | TTS，返回音频字节；音色别名 + 白名单校验；**新增 `response_format=wav`**（取 pcm 后本地补 44 字节头，否则是裸 PCM） |
| `POST /v1/images/generations` | 双后端：`seedream-4*` → 普通 Key `/api/v3`（4s，字段 `image`/`images`）；其余 → Plan `/api/plan/v3`（8–15s，字段 `reference_images`） |
| `_inline_local_media()` | 把 `messages` 里的本地图片/音频路径就地转 data URI（修复静默回退） |
| `/v1/registry` 扩展 | 新增 `embedding_models` / `embedding_dims` / `asr_models` / `asr_backends` / `tts_models` / `tts_voices` / `vision_models` / `image_backends` / `media_models` / `endpoints` |

## 7. 对项目意味着什么

**可以直接用的四件**：

1. **ASR 有了更快的云端路线**。现有 ASR Router 是 volc→baidu→whisper；方舟 WS 这条 6s 音频 1.16s、短句 0.68s，比 chat 路线快 28–31%，且几乎不随音频变长而变慢。作为第一顺位能省一次外部跳转。
2. **生图多了一个快通道且不吃 Plan 额度**。Seedream 4.0（4.1–4.6s）比 5.0-flash 快一倍，做资产批量（三视图、表情差分、道具）时用它更划算；5.0-pro 留给最终定稿。
3. **视觉理解不用再另找模型**。`doubao-seed-character-260628` 既是对话模型又是 VLM，1455ms 看图——`perception.py` 的视觉增强可以直接用当前对话模型，不用切模型。
4. **多模态向量能做跨模态检索**。文本和图像同一空间（cos 0.42），意味着「她记得你上次屏幕上的样子」这类需求第一次变得可实现；降维 1024 还不用重建向量库。

**要谨慎的三件**：

1. **别把 embedding 换到方舟**。单条 206–330ms 且不能批量，而 `bge-m3` 在本地是几十毫秒。换过去会让记忆写入变慢一个数量级。**只在本地 Ollama 不可用时当降级通道**。
2. **TTS 情绪仍然没救**。上一轮已实测该音色静默忽略 `emotion`，本轮复核资源档依旧只有 `seed-tts-2.0`——代理干脆不转发 emotion 参数，避免制造「已生效」的错觉。
3. **云端 3D 不要指望替代本地管线**。三款都只做图生 3D 且单张 >4 分钟，几何质量门槛（拓扑/骨/UV）与 2mini 是同一类问题，换更大模型不解决「从 2D 猜 3D」的根本矛盾——这条路线此前已判定放弃。

**一个新增选项**：`kimi-k3-1-pro` 1M 上下文，做长文档/长历史压缩可能比 deepseek 更划算，已入池但排在后面（2177ms）。

## 8. 复跑与排错

```bash
cd D:/LunaAI/project-nn/or_proxy
python probe_ark_capabilities.py            # 目录 + 向量 + TTS + ASR(双后端) + 生图/视频/3D
python probe_ark_capabilities.py --all      # 加全部 29 个对话模型连通性普查
python probe_ark_capabilities.py --json r.json
```

换 Key、续费、控制台改配置后都该跑一遍。判断口径：

- 目录里 `Published` 只说明**模型存在**，不代表你有权调；
- 控制台「已开通 + 有额度」也不代表 REST 可调（文本向量就是反例）；
- `404 ModelNotOpen` = 没开通；`404 InvalidEndpointOrModel.NotFound` = 模型 ID 不对或无权；
- `404 UnsupportedModel` = 这个模型不支持当前端点（Plan 与普通端点的可用集不同）；
- TTS 返回 0 字节但 HTTP 200 = 音色与资源档不匹配，别当成功；
- 提交任务返回 200 **不代表任务会成功**，3D/视频必须再查一次 `status`。
