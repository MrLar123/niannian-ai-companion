# 情绪旁路 + 表情联动 · 一期实施方案

> 目标：闭合「声音有情绪、脸没情绪」这条裂缝。
> 范围：文本/语音对话 → 情绪标签 → （VRM 表情 + 姿态 + TTS 韵律）。不含动作库。
> 本方案推翻了两次直觉假设，全部结论有实测数据支撑（§2）。工具已随文交付。
>
> **v2（2026-11-05）**：补齐「可用模型能力」这一层。—— 判定模型横评与
> `thinking:disabled` 开关（§2.7）、TTS 韵律四参数实测（§2.8）、字级时间戳（§7.1）、
> 时序设计（§8.1）、能力分配表与不采用清单（§13 / §14）。

## 0. 结论

**情绪判定的输入必须是「他说的话」，不是「她回的话」。**

这句话是整个方案的地基。因为她的台词太短——实测 20 条里 15 条不超过 8 个字
（"哦。""嗯。""不是。"），**文本里根本没有情绪信息**，任何标注方法都会失败。

正确的链路是并行旁路：

```
他说的话 ─┬─→ 规则层（<1ms）        ─→ EMO_STATE(rule)
          ├─→ LLM 判定（400~600ms） ─→ EMO_STATE(llm)，覆盖规则层
          └─→ 生成 + TTS（1.2s+）   ─→ 她开口
                                          ↑
前端 400ms 轮询 /api/last，取 emo ────────┘  （表情通常比她开口早到约 700ms）
```

四条硬结论：

| 结论 | 实测依据 |
|---|---|
| 主链路延迟增加 **0ms** | 判定在旁路线程跑，且比生成快（400~600ms vs 1200ms），天然不阻塞 |
| 判定命中率 **80%** | 50 条样本（44 条有期望），v3 判据；最大单标签占 20%，无垃圾桶 |
| **不要**让模型自己贴标签 | 同次输出 41%，且删掉 neutral 后另找 tired 当垃圾桶（30%+） |
| **不要**指望 TTS 原生情绪 | 官方文档里 unidirectional 端点**根本没有 `emotion` 字段**（§2.8） |

### 0.1 「模型能力」这一层的补充结论（2026-11-05 增补）

原方案写 TTS「只有 speech_rate，语速是主信号」——**这条是错的**，重读官方文档并实测后
发现还有第二个正交维度，以及一个此前以为不存在的能力：

| 能力 | 原判断 | 实测 | 对方案的影响 |
|---|---|---|---|
| 判定模型 | character 442ms / 76%（20 条） | **关思考 368ms；v3 判据下 400~600ms / 80%（50 条）** | 所有判定请求必须显式关思考（§2.7），否则部分模型 0% 命中且不报错 |
| TTS `speech_rate` | 唯一可用，`rate% × 0.6` 换算 | **1 点 ≈ 1% 语速，1:1**（§2.8） | 换算系数改掉，旧映射整体偏轻 |
| TTS `loudness_rate` | 未使用 | **生效**，RMS 动态 2.4 倍 | 新增"轻声/提声"维度，补上 shy / sad / tired 的听觉差 |
| TTS `post_process.pitch` | 以为没有 | **文档有、实测不生效**（噪声内） | 别再试，音高这条路在 plan 通道是死的 |
| 字级时间戳 | 记忆里"seed-tts-2.0 无" | **可用**，`enable_subtitle` 返回 `words[]` 带 startTime/endTime | 口型可脱谱、情绪表情可对齐到关键词发音时刻（§7.1） |

这五项合起来，把一期的效果上限从「脸在演、声音配合」抬到「**脸在演、声音有两个维度在配合**」。
仍然不是"声音在演"，但 shy 和 sad 终于能在听感上分开了。

| 3 | `pages/desktopvrm.html:2018 poke._face()` | 表情只由"戳一下"触发 | 与对话链路完全不通 |

隐性障碍（决定协议选型，不是风格问题）：

```python
# xiaoyun_server.py:499
_STAGE_PARENS = re.compile(
    r"[（(【\[][^）)】\]]{0,40}?[）)】\]]|〔[^〕]{0,40}?〕|<[^>\n]{0,24}>|\*[^*\n]{0,24}\*")
```

`<...>` 内 **24 字符以内**会被当舞台动作剥掉。所以业界通用的 AIRI 短标记
`<|ACT:happy|>`（13 字符）会被静默吞掉，而长 JSON 版本（40 字符）不会——
同一协议两种行为。**任何标记方案都必须避开这条正则**。本方案最终不需要标记，
但仍然记下这个坑：二期若加动作标签，必须用 `⟦⟧` 或 `%%` 一类定界符。

## 2. 八项实测（两次推翻假设 + 模型选型 + 参数生效性）

### 2.1 豆包 TTS 的 `emotion` 到底生不生效

同文本、同参数，24kHz PCM 解码算中位基频（自相关 + 抛物线插值）：

| 音色 | 无 emotion | happy | sad | angry |
|---|---|---|---|---|
| `zh_female_gaolengyujie_uranus_bigtts` | 182.7Hz / 2.98s | 185.2Hz / 3.00s | 182.7Hz / 3.00s | 183.6Hz / 3.00s |

四组全部落在 182–185Hz，时长全部 3.00s。**不生效**，且 HTTP 一律 200、无任何告警。

一个方法论上的坑：**只看"跨度"会误判**。第一次采样跨度 9.6%，但方向是反的
（sad 高于 happy），那是采样噪声；换方向性判据（sad<happy、sad 更慢、happy>neutral）
后 0/3 成立，才判出真结论。所以探测工具用方向而不看幅度，见 `tools/tts_emo_probe.py`。

文档写的"仅部分音色支持"，实际表现是**静默忽略**——最容易误判成"已生效"。

> 2026-11-05 补记：重读 `unidirectional` 完整参数表后发现，该端点**根本没有 `emotion`
> 字段**（全文 0 次命中）。所以不是"支持但不生效"，而是"这条路不存在"。
> 同一轮实测还发现 `speech_rate` / `loudness_rate` 是生效的，`pitch` 不生效——详见 §2.8。

### 2.2 换多情感音色能救吗

| 尝试 | 结果 |
|---|---|
| `seed-tts-2.0` + `*_emo_v2_mars_bigtts` | 返回 **0 字节** |
| `seed-tts-1.0` + 同上 | **HTTP 403**（资源未开通） |

当前账号在 2.0 资源下拿不到原生情感能力。一期 TTS 侧只做 `speech_rate` + `loudness_rate`
（两维均实测生效，见 §2.8；`pitch` 无效）。

### 2.3 假设一：让角色模型边说话边贴标签

`doubao-seed-character-260628`，system 含人设 + 禁括号 + `⟦emo:标签:强度⟧` 要求：

| 格式 | 标记出现 | 可解析 | 泄漏进正文 |
|---|---|---|---|
| `⟦emo:happy:0.8⟧` | 5/5 | 5/5 | 0 |
| `%%emo:happy:0.8%%` | 5/5 | 5/5 | 0 |
| `{"emotion":"happy",...}` | 5/5 | 5/5 | 0 |

格式全部通过。**但语义不行**——加了记忆/情境/长历史后跑 20 条：

- 标记载率 **100%**、塌缩率 0%，看起来完美；
- **命中率只有 41%**（标签不在期望集内）；
- 删掉 `neutral` 之后，模型把 `tired` 当成了新垃圾桶（6/20，占 30%），
  因为情境块写着"深夜 23:58、他加班到很晚"；
- 尤其：`"我明天要去相亲了"→ neutral:0.9`、`"你真好看"→ soft`、`"我今天升职了！"→ soft`。

**根因不是模型弱，是任务本身有问题**：模型是**先写出冷淡的台词，再给这句台词贴标签**，
标注被自己的表演带偏。它写"哦。"，就只能标 neutral。

**这个发现很重要**：只看"标记载率"会得出 100% 很好的错误结论。必须同时看
**命中率**和**最大单标签占比**。这两项后来成了回归闸门的核心指标。

### 2.4 假设二：让独立模型判断"她说的台词"

两阶段：角色模型生成台词（不带标记）→ 独立模型只看两句对话判情绪。

| 判断模型 | 命中率 | 延迟 |
|---|---|---|
| `doubao-seed-2-0-mini-260428` | 18% | avg 2.6s |
| `doubao-seed-2-1-pro-260915` | 超时 | — |

**比自标更差**。原因很直接：她的台词是"嗯。""哦。""不是。""2。"
——**输入是空信息，谁判都只能判 none**（13/17 判 none）。
延迟 2.9s 也不可接受（表情比语音晚 3 秒，等于没有）。

### 2.5 假设三：判断"他说的话"

同一批 20 条，判定的输入换成他的话，极短 prompt（只回一个词，`max_tokens=8`）：

| 模型 | 命中率 | avg | p90 |
|---|---|---|---|
| `doubao-seed-2-0-mini-260428` | 53% | 2611ms | — |
| `doubao-seed-character-260628` | **76%** | **442ms** | **679ms** |

**成立。** 而且这解释了为什么之前全错：情绪不是"她话里的副词"，
而是"**她对他这句话的反应**"。她的台词是她对情绪的执行结果，不是情绪的输入。

意外发现：`character` 微调模型判得比 `mini` 准，也快得多（442ms vs 2611ms）——
它对人设语境更敏感。判定模型默认就用它。

> 2026-11-05 复核：补上 `thinking={"type":"disabled"}` 后，`character` 进一步降到
> **368ms**（20 条口径 71~82%；扩到 50 条并换 v3 判据后是 80%，见 §4.2）。
> 首选不变，但这个开关必须加——不带它的模型
> 可能 0% 命中且完全静默。

### 2.6 5 个预设能撑起几个情绪

把初稿配方当 5 维向量算余弦：

| 对 | cos | 含义 |
|---|---|---|
| happy vs excited | **0.953** | 几乎同向，纯权重分不开 |
| happy vs shy | 0.922 | 同上 |
| soft vs tired | 0.881 | 同上 |
| soft vs shy | 0.853 | 同上 |
| annoyed vs jealous | 0.679 | 可分开 |

**决定了表达策略：3 组必须"姿态主导"**（§8）。只调 blendShape，
`happy/excited`、`soft/tired`、`happy/shy` 三对用户看不出区别。

### 2.7 判定模型横评：一个能让命中率从 0% 到 76% 的开关

新模型接进来之后重跑选型，意外撞上一个**静默失败**，值得单独记：

**判定请求必须下发 `thinking={"type":"disabled"}`。**

`max_tokens=8` 是为了压低延迟（只回一个词）。但带思维链的模型会先把 8 个 token
全花在 `reasoning_content` 上，`content` 为空、`finish_reason=length`，
解析出来就是 `None` → 全判 none。**HTTP 200，没有任何报错**，指标上表现为
"这个模型不行"，其实是预算被思维链吃光了。

实测（20 条全量，`temperature=0.1`、`max_tokens=8`；快速集为 6 条）：

| 模型 | thinking | 命中 | 塌缩 | 延迟 |
|---|---|---|---|---|
| `doubao-seed-character-260628` | 默认 | **14/17 = 82%** | 18% | p50 478ms |
| `doubao-seed-character-260628` | **disabled** | 4/4（快速集） | 0% | **368ms** |
| `deepseek-v4-1-flash-economy` | 默认 | **0/17 = 0%** | **100%** | 1005ms |
| `deepseek-v4-1-flash-economy` | **disabled** | 13/17 = 76% | 12% | 931ms |
| `doubao-seed-2-1-pro-260915` | 默认 | 超时（>30s） | — | — |
| `doubao-seed-2-1-pro-260915` | **disabled** | 4/4（快速集） | 0% | 1069ms |

三条结论：

1. **character 仍是最优**：关思考后 368ms（6 条快速集），比 economy 快 2.5 倍、比 pro 快 2.9 倍，
   准确率不低——它是角色微调模型，对人设语境敏感且不带思维链。
   （50 条全量 + v3 判据下是 400~600ms、命中 80%，见 §4.2）
2. **关思考是通用兜底**：任何模型加上这个字段都能从"判不出"变成"能判"，
   所以 `judge` 请求无条件带上，character 有没有思维链都不吃亏（实测还快了 23%）；
3. **2.1-pro 不适合做判定**：即使关思考也要 1069ms，p90 会破 1200ms 闸门。

用法：`tools/emo_model_probe.py --model X --no-think --full`。
换判定模型前必跑，别只看命中率——**先确认 `finish_reason` 不是 `length`**。

**代理层必须一起改（已改）**：`or_proxy.py` 的转发白名单 `BASE_FIELDS` 原先不含
`thinking`，客户端显式传的值会被**静默丢弃**；更糟的是 `build_payload` 的注入条件是
`k not in body`——body 里"有"这个键（只是没被转发），于是连 ark 上游的默认关思考
也被跳过。结果：**想关关不掉，想开开不了**，两边都静默。
已把 `thinking` / `reasoning_effort` 补进白名单，实测经代理请求
`deepseek-v4-1-flash-economy` + `thinking:disabled` 能直接回 `happy`
（`finish_reason=stop`、`reasoning_content` 为空）。

**判定不能走 `auto` 路由**。ark 上游配了 `no_thinking` 默认注入，但 OpenRouter
上游是 `no_thinking: None`。`auto` 在方舟额度耗尽时会落到 OpenRouter 的 reasoning
模型（nemotron 系），判定立刻退化成全 none，而且**主链路一切正常，只有脸不动**——
这种故障最难查。judge 必须写死模型名。

### 2.8 TTS 的可用旋钮：文档说的 ≠ 生效的

重读 `unidirectional` 端点的参数表（原方案只看了 5 个音色的 `emotion` 行为，
没看完整字段），再用方向性判据逐项实测。同文本、同音色
`zh_female_gaolengyujie_uranus_bigtts`，PCM 24kHz 解码后算中位基频 / RMS / 时长：

| 参数 | 文档 | 实测（`--times 3` 取中位） | 判定 |
|---|---|---|---|
| `emotion` | **不存在该字段** | — | 一期别再找，这不是"被忽略"而是"没有" |
| `speech_rate` | `[-50, 100]`，100 = 2 倍速 | 3.80s → **2.38s**(+60) / **5.43s**(−30) | **生效** |
| `loudness_rate` | `[-50, 100]`，100 = 2 倍音量 | RMS **1457** / 2354 / **3337**（−40/+0/+40） | **生效** |
| `post_process.pitch` | `[-12, 12]`，负=低沉 | +6 → 235.0Hz、−6 → 237.8Hz、基线 236.4Hz（基线自身抖动 229~243） | **不生效** |
| `enable_subtitle` | bool，字级时间戳 | 返回 `sentence.words[]`，每字带 `startTime/endTime/confidence` | **可用** |

复核离散度：时长在 +60 档 2.37~2.38、基线 3.79~3.81（差 <0.02s），−30 档 5.43~5.68
（慢速档服务端切分更碎，抖动 0.25s，但仍远小于 1.3s 的档间差）；RMS 波动约 2%。
**信噪比远大于抖动，结论稳**。`pitch` 恰恰相反，见下面第 ② 条。

三个必须写清的细节：

**① `speech_rate` 是 1:1 映射，原方案的 `× 0.6` 换算错了。**
3.80s 的基准，`+60` 压到 2.38s（**1.60 倍速**）、`−30` 拉到 5.43s（**0.70 倍速**）——
与文档公式 `1 + speech_rate/100` **完全吻合**，没有一点偏差。所以点值就是语速百分比增量。
旧代码按 edge-tts 的 ±8% 语义再乘 0.6，实际只给了 ±4.8，听感自然"调了也听不出"。

**② `pitch` 不生效这件事必须排除测量噪声才能下结论。**
第一次单次采样时 `+6` 的 F0 反而**更低**（219 vs 247），差点误判成"负向生效"。
改成重复 3 次后基线自身就在 229~243 之间抖，三组中位数 235 / 236 / 238 完全重叠——
**抖动大于差值，参数无效**。这是 §2.1 那个"只看跨度会误判"的同类坑，
`tools/tts_prosody_probe.py` 已内置 `--times` 与离散度打印。

**③ 字级时间戳要累积，首条是空的。**
流式返回里第一条 `sentence` 的 `words` 是 `[]`，后续 chunk 才填充：

```json
{"sentence": {"text": "今天过得还不错，你呢？", "words": [
  {"word": "今", "startTime": 0,     "endTime": 0.155, "confidence": 0.96},
  {"word": "天", "startTime": 0.155, "endTime": 0.305, "confidence": 0.97}]}}
```

按事件顺序累加即可，不要去重（不同 chunk 可能带同一句的不同片段）。
参数位置：放进 `audio_params`；放 `req_params` 会被静默忽略（不报错，只是没有 words）。

## 3. 最终架构

```
                        ┌──────────────── 旁路，不阻塞 ────────────────┐
用户说话 ──→ do_chat ───┤                                            │
   │                    │ [A] 规则层  emotion_rules(msg)  <1ms        │
   │                    │        ↓ 写 EMO_STATE(rule)                │
   │                    │ [B] 线程 judge(msg)  400~600ms             │
   │                    │        ↓ 写 EMO_STATE(llm)（覆盖 A）        │
   │                    └────────────────────────────────────────────┘
   │
   └──→ _brain_turn → brain_chat（1.0~2.0s）→ _publish_reply → TTS
                                                      │
                                        写 LAST(emo=EMO_STATE)
                                                      │
   前端 /api/last（400ms 轮询，fresh 与否都带 emo）───┘
                    ↓
              Face.set(label, intensity) → 插值 → expressionManager + 姿态
```

时序（实测值）：

| 时刻 | 事件 |
|---|---|
| 0ms | 收到他的话；规则层已出初值 |
| 450ms | LLM 判定回来，表情开始变化 |
| ~1200ms | 她开口（TTS 首包） |

**表情比她开口早约 700ms**——不是"不增加延迟"，而是"表情先到"。
这反而更像真人：先变脸，再说话。

### 3.1 为什么不用"同次输出标记"（虽然格式 5/5 通过）

| 维度 | 同次标记 | 旁路判定 |
|---|---|---|
| 命中率 | 41% | **80%** |
| 延迟 | 0 | 0（并行） |
| 正文污染风险 | 有（需剥离、需防 HISTORY 累积） | **无** |
| 换模型后稳定性 | 依赖格式遵循 | 依赖一次判词，弱得多 |
| 能否影响台词 | 不能（标签在文末） | 二期可用上一轮情绪注入 |

结论：旁路不仅更准，还更干净。格式遵循这种脆弱能力能不用就不用。

## 4. 判定合同

### 4.1 标签集（8 个，无 neutral）

```
happy  soft  annoyed  jealous  shy  sad  tired  curious
```

- 不设 `neutral`：用"判 none"表达平淡，避免垃圾桶（§2.3 的教训）；
- 不设 `excited`：并入 happy，靠 `intensity > 0.75` 触发加强配方（cos 0.953）。

### 4.2 判定 prompt（v3，50 条实测 80%）

```text
判断她对这句话的情绪反应，只回一个词：
happy soft annoyed jealous shy sad tired curious none。
被夸/被表白/被想念→shy；提到别的异性→jealous；抱怨/被催/被嫌→annoyed；
关心/撒娇/道谢/道晚安/留门→soft；低落/告别/要离开→sad；累/困/熬夜→tired；
好消息/炫耀/分享喜悦→happy；提问/追问/让人猜→curious。
只有当这句话是纯事实陈述或工具性请求（天气、报错、写代码、算术、日程确认）
才回 none；其余情况一律选最接近的一个词，不要因为'不确定'就回 none。
```

约束：`max_tokens=8`、`temperature=0.1`、`thinking:disabled`、
输入只有 `"他：" + msg`。**不要**把她的台词、记忆块、历史塞进去——
§2.4 已证明台词是噪声源，而记忆块会引入"深夜→tired"这类偏置。

#### 为什么从 v2 换成 v3：垃圾桶搬到了 none

把样本从 17 条扩到 44 条有期望的句子后，v2 立刻暴露问题：

| 判据 | 命中 | 塌缩 | p90 | 闸门 |
|---|---|---|---|---|
| v2（「平淡→none」） | 27/44 = **61%** | 16/44 = **36%** | 720ms | FAIL |
| v3（「只有纯事实/工具请求才 none」） | 35/44 = **80%** | 4/44 = **9%** | 500~880ms | **PASS** |

v2 把「晚安」「谢谢」「哼」「我刚跑完五公里」全判成了 none。这不是模型变笨了，
而是 **`平淡→none` 给了一个太大的逃生口**——模型分不清时一律说"平淡"。
这和 §2.3 那个"删掉 neutral 后 tired 变垃圾桶"是同一类失效，只是换了个出口。

v3 的做法不是删掉 none（那样会重演旧坑），而是**把 none 的适用面收到"纯事实/工具性请求"**，
并加一句"不要因为不确定就回 none"。代价是 prompt 多了 30 字、p90 从 720 涨到 500~880ms，
仍远低于 1200ms 闸门。

分布也健康（最大单标签 8/41 = 20%）：
`soft=8 jealous=8 sad=6 curious=5 tired=4 shy=4 annoyed=4 happy=2`。

三次采样命中在 35~36/44（**80~82%**），偏差与塌缩条目几乎逐条一致
（只有「我今天买了新手机」一次判 happy、一次判 none）——说明 `temperature=0.1` 下
判据本身是稳定的，剩下的抖动来自边界样本，不是随机性。

残留 5 条偏差都集中在"她的反应"与"她自己的状态"之间摇摆
（「你昨晚是不是没睡好？」判 tired、「你是不是不喜欢我」判 jealous），
这属于标注本身有歧义，不建议再改 prompt 硬凑——理由同 §2.3。

情境最多加一句，且必须带反向指令：

```text
情境：现在是深夜，他刚加班回来。只参考，不要因此默认 tired。
```

### 4.3 强度从哪来

判定只回一个词，没有强度。强度不靠模型，靠**规则 + 语气符号**：

| 信号 | 增量 |
|---|---|
| 感叹号 / `！` | +0.15（上限 0.9） |
| 连续重复标点（`。。`、`!!`） | +0.1 |
| 句末疑问 `？` | curious/jealous 类 +0.1 |
| 消息长度 < 6 字 | −0.15（话越短情绪越内敛，符合她的人设） |
| 默认 | 0.5 |

理由：强度是"表演幅度"，用户不要求它准，只要求"别每句都一个幅度"。
让模型再输出一个数字会重新引入格式遵循问题，不值。

### 4.4 三级降级

```
① LLM 判定成功      → label + conf=high，src=llm
② LLM 超时/失败/异常词 → 规则层结果（关键词表映射到新标签），src=rule
③ 规则也无命中      → none（表情回基线，不做变化）
```

规则层保留现有 `_EMOTION_RULES` 的词表，只改**输入**和**输出标签**：

| 旧档 | 新标签 | 输入 |
|---|---|---|
| 开心 | happy | msg（原来错用 reply） |
| 傲娇 | annoyed | msg |
| 吃醋 | jealous | msg |
| 心疼 | soft | msg |

再补 4 条高置信模式（覆盖 LLM 失败的常见场景）：
`气死/烦死/受够→annoyed`、`相亲/别的女生/她是谁→jealous`、`好累/困死→tired`、`升职/中奖/太好了→happy`。

新建 `emotion_rules.py`（纯函数、无依赖、可单测）：

```python
LABELS = ("happy", "soft", "annoyed", "jealous", "shy", "sad", "tired", "curious")
JUDGE_SYS = "..."          # §4.2 v3 原文（含"只有纯事实/工具请求才 none"）

```

改动清单：

| # | 位置 | 改法 |
|---|---|---|
| 1 | `xiaoyun_server.py` 新增 `EMO_STATE` + `_kick_emotion(msg)` | 全局状态加锁替换（`EMO_STATE = {...}` 单次赋值，原子）；起 daemon 线程跑 judge；带 `req` 递增号防串（连说两句时旧结果不许覆盖新结果）；**judge 请求体固定带 `"thinking": {"type": "disabled"}`**（§2.7：不带会让部分模型 0% 命中且不报错） |
| 2 | `_brain_turn(msg)` 入口 | 第一行调 `_kick_emotion(msg)`。**这是唯一新增调用点**，语音/文字两条路都过它 |
| 3 | `_publish_reply()` | 不再自己 `_detect_emotion(reply)`；改为读 `EMO_STATE`（若 `req` 不匹配则用规则层）。`emo` 写入 `LAST` 与返回 payload |
| 4 | `/api/last`（`:2399`） | 响应**无论 fresh 与否都带** `emo`（前端靠它拿表情，不能等台词就绪） |
| 5 | `_speak_proactively()` | 主动开口没有"他的话"，用情境意图当判定输入（`intent` 文案），同样 `_kick_emotion` |

关键设计：`_publish_reply` 仍是唯一发声出口，但**表情不再依赖它**——
表情走 `EMO_STATE` + `/api/last` 独立通道，因此主动开口、固定文案、
语音/文字四条路径自动全部覆盖，不需要逐个改。

TTS 映射（**两个维度都实测生效**，见 §2.8；数值按强度线性缩放，`intensity` 0.5 为基准）：

| 标签 | `speech_rate` | `loudness_rate` | 听感 | 标签 | `speech_rate` | `loudness_rate` |
|---|---|---|---|---|---|---|
| happy | +8 | +4 | 轻快、稍亮 | shy | **−6** | **−14** |
| soft | −4 | −10 | 放缓、放软 | sad | **−10** | **−8** |
| annoyed | +5 | +6 | 略快、压着声 | tired | **−16** | **−18** |
| jealous | +6 | +2 | 带刺、发紧 | curious | +4 | +2 |

**为什么音量这一维值得单独设计**：§2.6 已经证明 `shy / sad / tired` 三组的表情权重
余弦 > 0.85、光靠语速也分不开（都是"变慢"）。但它们的**音量—语速组合**不同：

- shy = 不怎么慢，但明显小声（不敢大声）；
- sad = 慢，音量中等偏低（闷）；
- tired = 又慢又轻，接近气声。

音量维度让这三者在**只靠听**的情况下也能区分，而这正是原方案放弃的部分。

换算规则（改掉原来的 `× 0.6`）：

```python
# speech_rate 点值 = 语速百分比增量（实测 1:1，+60 → 1.60 倍速）
def tts_params(label, intensity=0.5):
    """intensity 0.5 → 表值原样；1.0 → ×1.4；0 → ×0.6（不归零，归零就没情绪了）。"""
    r, l = TTS_TABLE[label]
    k = 0.6 + 0.8 * intensity
    return int(round(r * k)), int(round(l * k))
```

**逐句韵律**（廉价但有效）：长回复按标点切句，首句满强度、末句 `speech_rate −3`
收尾——「一句话说完情绪就散了」是最像机器的细节。她的回复常常只有一句
（"哦。"），所以这段代码要有 `len(sentences) > 1` 的短路，别为此把单句也切碎。

**音高这条路是死的**：`post_process.pitch` 实测无效（§2.8），而换音色会破坏人格一致性。
所以"激动时音调上扬"做不了，用 `loudness_rate` 抬高来代偿——听感上是"提了声"
而不是"尖了"，勉强够用。二期若真需要音高，只能找支持 `emotion` 的资源（当前账号无）。

## 6. 前端 `FaceMixer`

现在有四个写者，直接加第五个必然打架：

| 写者 | 写哪些 | 行为 |
|---|---|---|
| `driveBlink()` | `blink` | 每帧覆盖 |
| `driveMouth()` | `aa/ih/ou/ee/oh` | 每帧覆盖 |
| `poke._face()` | `surprised/angry/relaxed/happy` | 戳时写值，**退出时写 0** |
| 情绪（新增） | 同 poke 的 5 个 | 需长期持有 |

不改的话：戳一下结束 `_face(0)` 会把情绪清零 —— 表现是"戳完她突然面无表情"。
这不是概率问题，是必然。

改法：把 `poke` 从写者降级为**叠加项**，新建唯一合成器。

```js
const Face = {
  emo: {label: null, intensity: 0, ts: 0},    // 来自 /api/last
  overlay: [],                                 // poke 等一次性效果，带过期时间
  cur: {}, target: {},
  set(label, intensity, ts) { /* ts 单调，旧结果丢弃 */ },
  push(name, v, ms) { /* poke 用，不直接写 expressionManager */ },
  tick(t, dt) {
    // 1. target = 配方[emo] × intensity
    // 2. 说话让位：xiaoyunSpeaking 时整体 × 0.8（happy 自带嘴形会压掉元音）
    // 3. 叠加 overlay，clamp ≤ 0.85
    // 4. cur += (target-cur) × (1-exp(-dt/tau))   tau: 上升 0.18s / 衰减 0.55s
    // 5. 写 expressionManager + 姿态（headX/headZ/gazeYaw/gazePitch/breath）
  }
};
```

挂载：`window.__xyFrameHook`（`:2115`）内 `poke.tick(t)` 之后调 `Face.tick(t, dt)`。

情绪生命周期：收到新情绪重置计时；保持 `max(3s, 语音时长)`；到期按 τ=0.55s 回落基线，
**不做突然归零**（突然归零比不变还假）。

调试旋钮（沿用 `?tint=` 那套习惯）：
`?emo=jealous:0.7` 预览、`?emospeak=0|1` 关/开说话让位、`?emotau=0.18` 调插值。
`window.__xyDbg.face()` 返回 `{label, intensity, src, cur}` 供无头断言。

## 7. 表演配方表

`intensity` 乘到权重上，clamp ≤ 0.85（留余量给口型）。

| 标签 | happy | angry | sad | relaxed | surprised | 骨骼/其他（**加粗=主导信号**） |
|---|---|---|---|---|---|---|
| happy | 0.75 | — | — | 0.25 | — | 头 +2° 抬 |
| soft | 0.25 | — | — | 0.80 | — | 呼吸幅度 ×1.15、速度 ×0.9 |
| annoyed | — | 0.55 | — | 0.20 | — | **头 −3° 压、视线偏 ±8°** |
| jealous | — | 0.35 | 0.30 | — | 0.15 | **头 −2° + 视线侧移、上身微转** |
| shy | 0.40 | — | — | 0.35 | — | **头 −6° 低 + 视线下移 12°** |
| sad | — | — | 0.70 | 0.20 | — | 头 −5°、呼吸变浅 |
| tired | — | — | 0.25 | 0.60 | — | **呼吸周期 ×1.35、幅度 ×0.7、头 −4°** |
| curious | 0.20 | — | — | — | 0.45 | **头 +4° 侧倾、视线锁定** |

加粗项不是装饰：§2.6 的余弦表说明这几组光靠权重分不开，姿态才是主信号。
`Face.tick` 必须同时输出 `{expr:{...}, pose:{headX,headZ,gazeYaw,gazePitch,breath}}`。

### 7.1 字级时间戳带来的两件事（新增，不占一期工期）

§2.8 确认 `enable_subtitle` 能拿到逐字 `startTime/endTime`。同一份数据有两个用途，
优先级完全不同：

**立刻可做 · 口型**。`lipsync.js` 现在是"拼音→五元音→谱通量 onset 锚定 + 音节数先验"，
本质是在**猜**每个字什么时候出声。有了真时间戳，可以直接查表：
`当前时刻 t 落在哪个 word 的 [start,end)` → 取该字的韵母 → 元音权重。
好处不只是准，而是**不再需要音频分析**，CPU 占用下降、弱机器上不抖。
这条独立于情绪链路，建议先做——它是纯收益，没有审美争议。

**二期再做 · 逐字表情**。让表情在"关键词发音的瞬间"加强：

```
"我讨厌你。"  →  annoyed 基础权重 0.55
                 "讨" 起音 +400ms 处上冲到 0.75，说完 400ms 内衰减回 0.55
```

一期不做，理由：现在的表情连"8 个标签能不能分清"都还没验收，
再叠一层时间轴会把调参变量翻倍。但 `Face.tick` 的签名要预留
`timeline` 参数（`[{t0, t1, word}]`），二期接进来不改结构。

两个实现细节：
- 时间戳单位是**秒**（float），前端统一用毫秒，转换在入口处做一次；
- `startTime` 是相对**音频开头**的，不是相对"她现在开始说话"。基准要取播放起始时刻，
  否则整条时间轴会随网络抖动漂移。

## 8. TTS 的现实边界

分成两件事说，别混：

**做不到**：原生情感合成。§2.8 查证 `unidirectional` 端点**没有 `emotion` 字段**；
2.0 资源下 `*_emo_v2_mars_bigtts` 返回 0 字节、1.0 资源 403。这不是没配置，是资源不可用。

**做得到**：两维韵律。语速（0.74~1.69 倍）与音量（RMS 2.4 倍）都实测生效。
配合 §5 的逐句策略，"听感有起伏"能做到——但它来自"演得慢一点、轻一点"，
不是"模型理解了情绪"。因此：

- **视觉仍是主通道**：用户判断"她在生气"，主要来自表情与姿态；
- **声音是佐证**：语速+音量只负责"不拆台"，让表情不被声音反驳。

### 8.1 时序设计：别让低延迟吃掉表情提前量

这条容易做错，单独写：

| 路径 | 表情到达 | 语音出声 | 提前量 | 观感 |
|---|---|---|---|---|
| 现在（HTTP 整段） | ~450ms | ~1200ms | **~750ms** | 先变脸，再开口 |
| 双向流式 TTS（首包 607ms） | ~450ms | ~700ms | ~250ms | 脸和嘴几乎同时动，反而假 |
| 双向流式 + 故意延迟 250ms | ~450ms | ~950ms | **~500ms** | 最优 |

真人听懂了也要 300~800ms 才开口，**这个空档是表演的一部分**。
所以即使之后换成流式 TTS（`/v1/audio/speech?stream=1` 那条线），
也要在出声前留 `EMO_LEAD_MS = 400` 的余量。把它写死成常量，后续只调这一个数。

一期上限因此定为：**脸在演，声音在两个维度配合**。

| 指标 | 门槛 | 当前基线（50 条） | 一期实施后实测 |
|---|---|---|---|

真实链路比直连基线还快（377ms vs 500~880ms），原因是代理复用了到方舟的 keep-alive 连接，
而 `emo_probe.py` 每条都新建 TLS。**这也说明"判定延迟"应当以 `emo_e2e` 的口径为准**——
用户体感走的就是代理这条路。

**样本从 17 条扩到 44 条这件事本身就是一期的一部分**。原方案只有 17 条有期望的样本，
1 条差异就是 6 个百分点，塌缩率在 24~29% 之间乱跳、完全没有判别力。
扩到 44 条之后，同一套 v2 判据立刻从"76%、勉强过"掉到"61%、塌缩 36%"——
**问题一直都在，只是样本量掩盖了它**。这条教训比数字本身重要：
指标的可信度取决于样本量，17 条不足以支撑"闸门"这个说法。

扩样本时唯一的纪律：**标注宁可宽，不要为了指标收窄**（收窄就会重蹈 §2.3 的覆辙）。
残留的 5 条偏差集中在"标注本身有歧义"的句子上，那属于标注问题，不是判定问题。

A/B 截图：8 个标签各一张（`?emo=x:0.8`）+ 无情绪基线 1 张。
`shy / jealous / tired` 三张必须靠姿态能看出差别，否则调 §7 的姿态分量。

截图可以先过一道**多模态初筛**（`doubao-seed-2.1` 原生视觉，问"这张脸表达什么情绪"），
把结果和期望标签对一遍，能快速发现"8 个配方里有 3 个渲染成了同一张脸"这类硬伤。
但它**不能替代目视**：动漫脸的眉毛/嘴角语义和真人不同，模型给的分可能整体偏低。
用法是"排序用"——先看它认为最像的三张是不是同一类，而不是拿它的分数当验收线。
（这条尚未实测，等 `Face.tick` 能出图后再校准它的可用性。）

## 11. 风险

| 风险 | 概率 | 处置 |
|---|---|---|
| **姿态与眼神追随打架** | **高** | `gaze.update()` 也写 head 骨骼。`Face` 的姿态必须走**加法偏移**并让 gaze 后写，或直接在 gaze 内合并。顺序错了不报错，只表现为"说话时头在抖"。宁可先不做姿态，也不要两处都写绝对旋转 |
| 判定被情境块带偏成 tired | 中 | prompt 里不塞记忆/历史；情境最多一句且带反向指令 |
| 连说两句时旧判定覆盖新表情 | 中 | `req` 递增号，线程回来校验后才写 |
| 说话时 `happy` 压掉口型 | 中 | 权重上限 0.85 + 说话 ×0.8；`?emospeak=0` 可关 |
| 换模型后判定退化 | 中 | `emo_probe.py` 作为换模型闸门，命中 < 60% 不许上线 |
| LLM 判定超时（网络） | 低 | 三级降级到规则层，表情照旧有初值；判定线程 `daemon=True` 不拖进程退出 |
| **判定全判 none 却不报错** | 中 | 思维链模型吃光 `max_tokens`（§2.7）。judge 固定 `thinking:disabled`、写死模型名不走 auto；日志必须打 `finish_reason`，出现 `length` 立刻告警——这是唯一能看见的信号 |

最高风险是第一条，且它**不会报错**。实现顺序上先做表情、后做姿态，
先确认 `Face` 与 `gaze` 的写入顺序再动头部。

## 12. 二期预留

1. **动作标签**：`judge` 的 prompt 扩一个词表即可（`laugh/nod/tilt_head/shrug`），
   协议与情绪同构，解析器不用改。注意定界符仍要避开 `_STAGE_PARENS`。
2. **情绪影响台词**：把**上一轮**情绪注入生成 prompt（"你刚才有点吃醋，语气还没缓过来"）。
   延迟一轮 = 零延迟代价，且能做出"情绪残留"的真实感。这是本方案唯一能低成本提升
   台词表现力的口子。
3. **长期心情**：`memory_store.set_profile("mood", ...)`，滑动的 valence 值，
   让"她今天心情不好"跨轮次成立。`EMO_STATE` 的结构可直接喂过去。
4. **自定义 ShapeKey**：`shy/jealous/tired` 现在靠姿态硬凑；§2.6 的余弦表就是
   "该先雕哪几个"的优先级依据（先雕 cos > 0.85 的对）。

## 13. 能力分配表（每个环节为什么用这个）

| 环节 | 用什么 | 为什么不用别的 |
|---|---|---|
| 粗判 | 纯 Python 规则 | <1ms、零 token；LLM 回来前先让脸有反应 |
| 判定 | `doubao-seed-character-260628` + `thinking:disabled`，**不走 auto** | 最快（368~600ms）且 80%（§4.2）；pro 关思考仍 1069ms（p90 破闸），economy 931ms 慢 2.5 倍；auto 可能落到没关思考的上游导致全判 none |
| 表情 | VRoid 14 预设中的 5 个 + 姿态 | VRoid 只导出预设，custom expression 恒 0；姿态是 §2.6 余弦表的必然结果 |
| 韵律 | `speech_rate` + `loudness_rate` | `emotion` 字段不存在；`post_process.pitch` 实测无效 |
| 口型 | 字级时间戳（`enable_subtitle`） | 已有 lipsync 是"猜"，有真值就不该继续猜 |
| 情境 | 最多一句 + 反向指令 | 记忆块/历史会把判定带偏成 tired（§2.3） |
| 验收 | `emo_probe` / `emo_model_probe` / `tts_prosody_probe` | 各自管"准确率""选型""韵律生效性"，互不替代 |

### 15.2 与方案不同的三处

**① 判定回 `none` 也要覆盖规则层。** 方案只写了"LLM 成功 → src=llm"，没说 none 怎么办。
实施时踩到：模型回 `none` 被当成"没解析出标签"，于是**保留了规则层结果**——
`好累啊，加班到现在` 规则层给 tired、模型说 none（其实它认为这句是平淡抱怨），
最终表情演的是 tired。这是"两个判据打架，弱的那赢"。
现在把 `none` 当有效结论：`none` → `label=None, src=llm`，覆盖规则层；
而拼错/两个标签/被 max_tokens 截断仍算失败，保留规则层。
`emo_e2e.py` 的 `--timeout` 卡住 8s 就是这个 bug 的副作用（等不到 `src=llm`）。

**② `_cmd_say` 也要挂判定。** 方案说"`_brain_turn` 是唯一新增调用点"，但语音指令轮
（"换个音色"）走 `_cmd_say` 不经过 `_brain_turn`，表情会停在上一条的情绪上。
在 `_cmd_say` 里补了一次 `_kick_emotion(msg)`——仍然只看他的话。

**③ 呼吸只改幅度，不改周期。** 方案写"tired 呼吸周期 ×1.35"，但呼吸的相位在
`animateBones` 内部（`sin(t*1.4)`），`Face` 在它之后运行、只能叠幅度；
硬改周期会和挤压/取景抢写 `rig.scale`（那是踩过的坑）。
所以 tired 的实际表现是"呼吸更深更重"（幅度 1.27），sad 是"变浅"（0.85）——
听感/观感上仍能分开，但不是方案原文的"变慢"。要真改周期，得把呼吸抽成独立控制器。

### 15.3 实测到的数字

| 项 | 结果 |
|---|---|
| 真实链路判定 | **12/12 走通 LLM**，297~391ms，p90 **377ms**（经代理，比直连基线快） |
| 命中 | 10/10（有期望的样本） |
| 规则层兜底 | 每条都在 LLM 前 <1ms 落地（`test_rule_layer_lands_immediately` 守这条） |
| 8 标签表情权重 | 与配方 × 强度一致（如 shy 0.8 → `happy=0.31 relaxed=0.27`） |
| 姿态分离 | shy/sad/tired：姿态差 0.086/0.099/0.013，呼吸差 0.133/0.271/0.404 |
| 画面差异（128×128 灰度） | 各标签 vs 基线 1.0~3.7；shy~sad 2.7、sad~tired 2.6 |
| 戳一下 | `poke._face(0)` 后 `angry` 0.28 → 0.28，标签仍是 jealous |

sad/tired 的姿态差只有 0.013（本来就只差 1° 低头），靠呼吸幅度分开（0.40）——
所以验收脚本的判据写成"姿态 **或** 呼吸分开"，而不是硬要求姿态角。
这一条是实施时调整的：原方案只看姿态，实际会把 sad/tired 判成"没分开"。

### 15.4 已知限制（一期不解决）

1. **没做目视验收**：数值上 8 个标签各有不同的权重/姿态，但"看起来像不像"必须人眼判断。
   桌面上说几句带情绪的话（或 `?emo=shy:0.8` 逐张看）比任何自动化都准。
2. **表情覆盖视线**：情绪激活期间 `Face` 会绝对写眼球（要"低头不敢看"），
   代价是这几秒不追鼠标。回落时写一次 home 交还给 `gaze`。
3. **`emo` 只随 `/api/last` 走**：如果页面是纯文字聊天（不轮询 last），表情不会动。
4. **判定模型写死 `doubao-seed-character-260628`**（可用 `XIAOYUN_EMO_MODEL` 覆盖），
   不走 `auto`——auto 可能落到没关思考的上游，导致全判 none 且不报错。
5. **TTS 韵律在流式与整段两条路上都生效，但逐句只在流式路径**（`stream_pcm` 分段），
   整段路径是一次性请求，没有"末句收尾"。
