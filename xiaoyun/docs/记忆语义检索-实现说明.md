# 长期记忆 · 语义检索实现说明

> 一句话：记忆库从"关键词命中"升级为"关键词 + 语义"双路召回。
> 向量侧由 **Ollama 托管的 bge-m3** 提供（GPU 推理，约 664MB 显存 / 26ms）。

## 1. 要解决的问题

原检索是 SQLite FTS5 + 自建中文 bigram（`memory_store.py`）。它对**字面重叠**有效，
但存在结构性盲区：

| 存的 | 用户问的 | 纯 FTS5 | 现在 |
|---|---|---|---|
| 用户养了一只叫豆豆的猫 | 猫毛过敏怎么办 | 召回 0 条 | 命中养猫那条 |
| 用户是程序员，经常加班到深夜 | 你几点睡啊 | 召回 0 条 | 命中加班那条 |

原因是中文同义/上下位关系（猫 ↔ 猫毛、程序员 ↔ 加班）没有任何字面重合。
库越小越不明显，但按每轮抽取一条的速度，几百条之后这个盲区会天天出现。

## 2. 架构（2026-10-19 改为 Ollama 托管）

```
桌宠后端 (8090, Miniconda py3.10, 无 torch)
    │  EmbedClient.embed()  ->  POST 127.0.0.1:11434/api/embed
    │                           {model:"bge-m3", input:[...], keep_alive:"30m",
    │                            options:{num_gpu:99}}     ← GPU，约 664MB 显存
    ▼
Ollama (11434, 本机既有服务，非小芸独占)
    │  bge-m3  568M 参数 · 1024 维 · 8K 上下文 · 100+ 语言
    ▼
data/memory.db   facts.emb (BLOB, 1024×float32 = 4096 字节)
```

**为什么从自建服务迁到 Ollama**：早前那版是 `embed_service.py`（8092，bge-small-zh，
sentence-transformers + torch cu128 跑在 hunyuan3d 的 venv 里）。它能用，但代价是
把 torch 那套依赖绑在项目里 —— 上次装 `sentence-transformers` 就把 `transformers`
从 4.46.3 顶到 5.x，直接带坏了 Hunyuan3D-2，只能回滚锁版本。Ollama 本机本来就在用，
模型交给它托管，这套冲突从此不存在。

## 3. 关键设计

### 3.1 GPU 推理（`num_gpu=99`）

Hunyuan3D 是低频使用，需要腾卡时手动 `ollama stop bge-m3` 就好，因此平时
让 bge-m3 常走 GPU（每轮对话都要检索一次，26ms 和 80ms 的差别会落在首包延迟上）：

| 场景 | GPU（当前） | CPU（旧） |
|---|---|---|
| 单次检索（1 条 query vs 全库 12 条） | **24~125ms**（稳定态均值 ~35ms） | 49~66ms |
| 批量入库（2 条文本） | 26ms | 80ms |
| 首次加载权重 | 2.4s（冷）/ 17s（从 CPU 状态切换） | 2.4s |
| `ollama stop` 腾卡后首次检索 | 3.0s 自动重载回 GPU | — |
| 显存占用 | **664MB**（`ollama ps` 显示 100% GPU） | 0 |

`keep_alive=30m`：比默认长得多，避免间隔几分钟的对话反复重载 1.2GB 权重；
又不常驻，长时间没人说话后自动把 664MB 还给显卡。（项目铁律：**禁止 `keep_alive=-1`**。）

**抢不到卡时不会失忆**：GPU 请求失败（3D 生成正在吃满显存）会自动用
`num_gpu=0` 重跑一次并记住 `cpu_fallback`；10 分钟后再自动重试 GPU。
两个都失败才退化为关键词检索。这条分支由 `tools/test_embed_fallback.py`
用 mock 服务覆盖（回落 / 全失败 / 到期复归三条路径）。

**启动不被冷启动拖住**：维度探测 + 旧向量迁移 + 存量补建全部丢在后台线程
（`_warm_embeddings`）。GPU 首次加载是秒级的，同步做会把"能响应 /api/health"
的时间往后推，启动脚本容易误判成没起来；代价只是最初几秒记忆退化为关键词。

### 3.2 RRF 融合
两路各出一个有序列表，用 Reciprocal Rank Fusion 合并（`k=60`，名次从 1 起算）：

```
score = -Σ 1/(60 + rank)        # 负号沿用"越小越相关"的既有排序方向
```

- **FTS5 路**：精确命中优先（"咖啡"这种词只有字面路靠得住，语义路会把它拉向"奶茶/饮料"）。
  排序里保留老的高频命中项对数加权（`hits`），避免语义路把冷门长尾顶上来。
- **向量路**：语义命中兜底（字面零重叠的情况）。

### 3.3 维度迁移（换模型必须做的一步）
`emb` 存的是 float32 原始字节，1024 维 = 4096 字节、512 维 = 2048 字节。
`_vector_hits` 会跳过长度不符的向量 —— **不报错、也不召回**，静默失忆比报错更难发现。
所以 `MemoryStore` 提供 `purge_mismatched_vectors(dim)`：后端启动时先探一次真实维度，
把异维向量置空，再 `backfill()` 重嵌。实测 12 条事实重嵌耗时 **0.66s**。

### 3.4 降级是设计的一部分
| 情况 | 行为 |
|---|---|
| Ollama 没起 / 模型没拉 | 后端照常启动，检索退化为纯 FTS5；`/api/health` 的 `memory_semantic=false` |
| 服务中途挂了 | 客户端 30s 掉线缓存，只付一次连接失败的代价，之后每 30s 自动重试 |
| 服务晚于后端起来 | **不需要重启后端**：客户端不是启动时一次性探活，下一次调用即恢复 |
| 显存被 3D 占满 | GPU 失败 → 自动 CPU 重跑一次 → 10 分钟后自动重试 GPU |
| 向量维度不对 | 启动时自动清空 + 重嵌（见 3.3） |

注意 `/api/health.memory_semantic` 的语义是"**最近一次调用真的成功过**"，不是
"客户端是否存在" —— 客户端是始终注入的（为了服务晚起能自愈），若按存在性判断会永远报 true。
`/api/health.memory_embed` 会显示实际推理位置：`bge-m3@ollama dim=1024 gpu`
（异常时为 `cpu_fallback`）。

## 4. 运维

```powershell
# Ollama 本身
& "C:\Users\Administrator\AppData\Local\Programs\Ollama\ollama.exe" serve
& "C:\Users\Administrator\AppData\Local\Programs\Ollama\ollama.exe" list
& "C:\Users\Administrator\AppData\Local\Programs\Ollama\ollama.exe" pull bge-m3   # 1.2GB
& "C:\Users\Administrator\AppData\Local\Programs\Ollama\ollama.exe" ps            # 看 PROCESSOR / SIZE
& "C:\Users\Administrator\AppData\Local\Programs\Ollama\ollama.exe" stop bge-m3   # 跑 3D 前腾卡
# 不用手动"装回来"：stop 之后第一次检索会自动重载回 GPU（约 3s，只一次）

# 探活（注意 --noproxy，本机直连）
curl --noproxy '*' http://127.0.0.1:11434/api/tags
curl --noproxy '*' http://127.0.0.1:11434/api/embed -d "{\"model\":\"bge-m3\",\"input\":[\"测试\"],\"options\":{\"num_gpu\":99}}"
```

**切回旧的自建服务**（保留 `embed_service.py` 作为后备，默认不再自动启动）：

```powershell
set XIAOYUN_EMBED_BACKEND=http
set XIAOYUN_EMBED_URL=http://127.0.0.1:8092
# 手动起：D:\LunaAI\hunyuan3d\venv\Scripts\python.exe D:\LunaAI\xiaoyun\embed_service.py
```

启动链：`Start-Xiaoyun.ps1` 的 1.8 节会在后端之前探活 Ollama（没起就拉起，
但**不会自动 pull 模型** —— 1.2GB 不该在开机流程里静默下载）。
Ollama 是**共享服务，不由小芸独占**：Stop 脚本不杀 11434。

## 5. 文件清单

| 文件 | 作用 |
|---|---|
| `xiaoyun_server.py` → `EmbedClient` | 双后端客户端（ollama / http），30s 掉线缓存、直连绕过代理、记录真实维度 |
| `memory_store.py` | `emb` 列 + RRF 混合检索 + `backfill()` + `purge_mismatched_vectors()` |
| `embed_service.py` | 旧方案（8092, bge-small 512 维），保留作后备，默认不再启动 |
| `models/bge-small-zh-v1.5/` | 旧模型权重（95.8MB），后备方案才用；不留可删 |
| `tools/test_memory_e2e.py` | 真实 Ollama 的 A/B、降级、维度迁移验证 |
| `tools/test_embed_fallback.py` | GPU→CPU 回落 / 全失败 / 到期复归三条分支（mock，不占显卡） |

## 6. 已验证（Ollama bge-m3 / GPU）

- `memory_store.py` 自测 36 项全过（含维度一致/变化/重嵌三态）。
- `tools/test_memory_e2e.py` 全过：
  - 语义盲区用例「猫毛过敏怎么办」→ 混合检索命中"养了只猫"，纯 FTS5 返回 0 条；
  - 精确查询「咖啡」两条路径都保持首位；
  - 服务指向死端口时安静降级、不抛异常；
  - 生产库 12 条事实完成 512→1024 迁移，无空缺、无异维。
- `tools/test_embed_fallback.py` 11 项全过（mock 500 模拟显存不足）。
- 真实后端运行时（Miniconda 3.10 + `_init_memory_and_context`）：`dim=1024`、
  `gpu_state=gpu`、`ollama ps` 100% GPU / 664MB、稳定态检索 17~89ms（均值 ~35ms）。

## 7. 能力边界（实测，非推测）

"所有本地模型都由 Ollama 托管"做不到，项目里 4 个本地模型只有 embedding 能迁：

| 模块 | 本地模型 | Ollama | 原因 |
|---|---|---|---|
| 记忆 embedding | bge-m3 | ✅ 已迁 | — |
| ASR 兜底 | faster-whisper-small | ❌ | `ollama.com/library/whisper` 实测 404；API 只接受文本/图像 |
| TTS 本地备选 | GPT-SoVITS | ❌ | 语音合成不在 Ollama 支持的模型架构内 |
| 3D 生成 | Hunyuan3D-2mini | ❌ | 扩散模型不在 llama.cpp 的架构范围内 |
